# AI-Native Bio-Compiler — Codons 0.17

Codons — миниатюрный язык и его компилятор на чистом C11: читает строгий
триплетный `.dna`, проверяет программу статически и исполняет — через JIT в x64
на Windows либо через встроенный эталонный интерпретатор на любой ОС. Ни LLVM,
ни ассемблера, ни внешних зависимостей: весь компилятор — руками написанный C.

**Зачем.** LLM-агенту нужно исполнять маленькие сгенерированные функции так,
чтобы это было безопасно и проверяемо. Codons даёт: статически доказанную
инициализацию всех регистров до запуска; детерминированный бюджет в миллион
шагов вместо таймаута по стенке; capability-модель ввода-вывода (программа не
видит ни ФС, ни сеть — только каналы, которые хост выдал явно); два независимых
бэкенда с командой `verify`, требующей их полного согласия; и ошибки в JSON
с подсказками и `line_text`, пригодные для автоматической починки.

**Пример целиком** — сумма 1..n, девять строк:

```text
GENE main i32/1     # main(n): сумма 1..n, n ≥ 1
LOAD r1 0           # сумма = 0
LABEL loop _
ADD r1 r0           # сумма += n
SUB r0 1            # n -= 1
JNZ r0 loop
MOV r0 r1
RET r0 _
END _ _
```

```powershell
codons run sum.dna 10
```

Результат: `55`. Каждая инструкция — ровно три поля: операция и два операнда.
Пропущенные `_` однозначно восстанавливаются `codons fix`.

**Для кого это.** Для агентов и оркестраторов, которым нужен безопасный,
верифицируемый сэндбокс-исполнитель маленьких функций: модель пишет `.dna`,
`check` валидирует, `test` гоняет CSV-примеры, `verify` сверяет два бэкенда,
`run` исполняет в пределах бюджета. Это не язык общего назначения — это
контрактный исполнитель для сгенерированного кода.

**Измеренная точность LLM.** Одна и та же модель (kimi-k3, одна попытка,
свежий контекст, без доступа к репозиторию) решала 25 задач на трёх дорожках:
Codons с минимальной грамматикой — **21/25** (84%; классы ошибок: формат полей,
неинициализированный регистр, run-fault `NARROW`); Codons с [LLM.md](LLM.md) —
**25/25**; Python — **25/25**. Паритет с Python по точности достигается
документацией; дальше начинаются преимущества формата: статические гарантии,
детерминированный бюджет и verify-оракул. Методика, таблицы и классы ошибок —
в [docs/llm-eval-experiment.md](docs/llm-eval-experiment.md); харнес и задачи —
в [tests/llm_eval/](tests/llm_eval/).

**Платформы.** Полная сборка с JIT — Windows x64. На Linux и macOS собирается
интерпретаторный вариант без JIT: `cmake -DCODONS_NO_JIT=ON` — работают все
команды, кроме `verify` и `emit` (они честно сообщают об отсутствии JIT).
Каждый push гоняет CI на трёх системах: ubuntu-latest и macos-latest
(интерпретатор) плюс windows-latest (полный JIT и тесты ядра) —
см. [.github/workflows/ci.yml](.github/workflows/ci.yml).

История изменений по версиям — в [CHANGELOG.md](CHANGELOG.md);
история тестирования — в [TESTING.md](TESTING.md).


## Переносимая версия

Распакуйте `Codons-0.17.0-windows-x64.zip` и откройте PowerShell в папке с `codons.exe`:

```powershell
.\codons.exe new hello.dna
.\codons.exe run hello.dna 10 20
.\codons.exe run examples\price.dna 3 250
.\codons.exe run examples\threshold.dna 75 60
.\codons.exe run examples\clamp.dna 150 100
.\codons.exe run examples\sum.dna 10
.\codons.exe run examples\factorial.dna 5
.\codons.exe run examples\branch.dna -4 9
```

Результаты: `30`, `750`, `1`, `100`, `55`, `120`, `9`.
Компилятор C и Python для запуска не нужны.
`new` отказывается перезаписывать существующий файл.
Программа использует системную Universal C Runtime; переносимая сборка рассчитана
на Windows 10/11 x64. Установщик и изменение PATH не требуются.

Готовые примеры можно проверить одной командой:

```powershell
.\codons.exe test examples\sum.dna examples\sum.csv
```

Ожидаемый итог: `Tests: 4 total, 4 passed, 0 failed`.

## Быстрый запуск

Понадобятся CMake и GCC/MinGW (проверено на GCC 15). В PowerShell из корня проекта:

```powershell
.\build.ps1
.\build\codons.exe run .\examples\main.dna
```

Результат: `30`. Скрипт собирает Release и запускает тесты.
Для Debug: `.\build.ps1 -Configuration Debug`.
Чтобы также собрать переносимый архив: `.\build.ps1 -Package`.
Если локальная политика PowerShell запрещает запуск скриптов, выполните сами команды:

```powershell
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_C_COMPILER=gcc -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

На Linux и macOS собирается интерпретаторный вариант без JIT:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCODONS_NO_JIT=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

В нём работают `run` (через интерпретатор), `interpret`, `check`, `test`,
`dump`, `fix`, `live`; `verify` и `emit` требуют JIT и сообщают об этом явно.

## Пример языка

```text
GENE add i32/2
ADD r0 r1
RET r0 _
END _ _

GENE main i32
LOAD r1 10
LOAD r2 20
CALL add r1,r2
RET r0 _
END _ _
```

Каждая значимая строка содержит ровно три поля, разделённых пробелами или табуляцией.
Пустые строки и комментарии с `#` разрешены. UTF-8 BOM, CRLF, LF и последняя строка
без перевода строки поддерживаются. Опкоды и имена чувствительны к регистру.
Идентификаторы: `[A-Za-z_][A-Za-z0-9_.]*`, до 63 символов; точка не может быть
первым или последним символом и нужна для точечных имён полей `STRUCT` и их дампа.

| Кодон | Значение |
|---|---|
| `GENE name i32` | Функция без аргументов, возвращает i32; эквивалент `i32/0` |
| `GENE name i32/1` | Один аргумент i32, доступен как `r0` |
| `GENE name i32/2` | Два аргумента i32, доступны как `r0`, `r1` |
| `GENE name i32/N` | N аргументов i32 (0–4), доступны как `r0`…`r(N-1)` |
| `LOAD rN 10` | Записать десятичное целое i32 в регистр |
| `VAR total 0` | Объявить локальную переменную i32 с начальным значением |
| `STRUCT p x,y` | Сахар: объявить одноячеечные локали `p.x`, `p.y` с нулями (0.16) |
| `ARRAY items 16` | Объявить локальный массив из 16 нулей |
| `PARAM items r0` | Принять массив; входной `r0` задаёт длину доступной части |
| `GET rN total` | Прочитать переменную в регистр |
| `SET total rN` | Записать регистр в переменную |
| `AGET rN items,rM` | Прочитать элемент с индексом из `rM` в `rN` |
| `ASET items rN,rM` | Записать значение `rM` в элемент с индексом из `rN` |
| `LEN rN items` | Записать длину массива в регистр |
| `READ items rN` | Скопировать входной список в массив, записать количество элементов в `rN` |
| `WRITE items rN` | Подготовить первые `rN` элементов массива для вывода |
| `SLOAD rN "text"` | Записать в регистр хэндл строкового литерала |
| `SLEN rN rM` | Длина строки по хэндлу `rM` в байтах |
| `SGET rN rM,rK` | Байт строки `rM` с индексом из `rK` |
| `SCAT rN rM,rK` | Конкатенация строк `rM` и `rK`, новый хэндл в `rN` |
| `SEQ rN rM,rK` | `rN = 1`, если строки `rM` и `rK` равны побайтово, иначе `0` |
| `PRINT rN _` | Записать байты строки `rN` в выданный хостом канал печати |
| `MOV rN rM` | Скопировать значение |
| `ADD rN rM` | `rN = rN + rM` |
| `SUB rN rM` | `rN = rN - rM` |
| `MUL rN rM` | `rN = rN * rM` |
| `DIV rN rM` | Знаковое целочисленное деление, результат в `rN`, округление к нулю |
| `MOD rN rM` | Знаковый остаток от деления, результат в `rN` |
| `AND rN rM` | Побитовое И, результат в `rN` |
| `OR rN rM` | Побитовое ИЛИ, результат в `rN` |
| `XOR rN rM` | Побитовое исключающее ИЛИ, результат в `rN` |
| `NOT rN _` | Инвертировать все 32 бита `rN` |
| `LAND rN rM` | `rN = 1`, если оба прежних значения ненулевые, иначе `0` |
| `LOR rN rM` | `rN = 1`, если хотя бы одно прежнее значение ненулевое, иначе `0` |
| `LXOR rN rM` | `rN = 1`, если ровно одно прежнее значение ненулевое, иначе `0` |
| `LNOT rN _` | `rN = 1`, если прежнее значение нулевое, иначе `0` |
| `SHL rN rM` | Сдвинуть `rN` влево на число бит из `rM`, освободившиеся биты — нули |
| `SHR rN rM` | Сдвинуть `rN` вправо с заполнением нулями |
| `SAR rN rM` | Сдвинуть `rN` вправо с сохранением знака |
| `EQ rN rM` | `rN = 1`, если значения равны, иначе `0` |
| `LT rN rM` | `rN = 1`, если прежнее `rN < rM`, иначе `0`; сравнение знаковое |
| `MIN rN rM` | Записать меньшее из двух знаковых значений в `rN` |
| `MAX rN rM` | Записать большее из двух знаковых значений в `rN` |
| `WLOAD wN value` | Загрузить литерал i64 в широкий регистр `w0..w3` (0.15) |
| `WMOV`…`WMAX wN wM` | 64-битные `MOV ADD SUB MUL DIV MOD AND OR XOR SHL SHR SAR MIN MAX`; арифметика по модулю 2⁶⁴ |
| `WNOT wN _` | Побитовое 64-битное отрицание |
| `WEQ rN wM,wK` / `WLT rN wM,wK` | 64-битное сравнение (биты / знаковое); флаг 0/1 в `rN` |
| `WIDEN wN rM` | Знаковое расширение i32 → i64 |
| `NARROW rN wM` | Сужение i64 → i32; ошибка, если значение не помещается в i32 |
| `CALL name _` | Вызов без аргументов; результат в `r0` |
| `CALL name rN` | Вызов с одним аргументом; результат в `r0` |
| `CALL name rN,rM,…` | Вызов с аргументами (до четырёх регистров через запятую); результат в `r0` |
| `CALL name items,rN,…` | Передать массив, длину из `rN` и ещё до трёх чисел; результат в `r0` |
| `LABEL name _` | Объявить метку внутри текущей функции |
| `JMP name _` | Безусловно перейти к метке |
| `JZ rN name` | Перейти к метке, если `rN == 0` |
| `JNZ rN name` | Перейти к метке, если `rN != 0` |
| `RET rN _` | Вернуть значение регистра |
| `END _ _` | Завершить функцию |
| `IMPORT math.dna _` | Подключить модуль вне функции |

Вызовы могут быть рекурсивными (0.14): не глубже 256 активных генов и не больше
262 144 ячеек i32 локальных данных во всех активных кадрах (1 MiB). Превышение —
ошибка выполнения `call depth limit reached` или `call frame memory exhausted`
с файлом и строкой, одинаковая в JIT и интерпретаторе. Подробности — в разделе
«Рекурсия» ниже.

На функцию выделяется до 256 локальных регистров `r0`…`r255` (потолок 8-битной
упаковки операндов). Вызов сохраняет регистры вызывающей
функции, кроме `r0`, куда записывается результат. До чтения регистр нужно
инициализировать на каждом возможном пути к месту чтения.
`main` принимает от 0 до 4 чисел согласно своей сигнатуре;
при запуске нужно передать ровно это количество. Например,
`GENE main i32/2` получает два числа из команды `run file.dna 10 20` в `r0`, `r1`.
`ADD`, `SUB`, `MUL` вычисляются по модулю 2³²; результат выводится как знаковое i32.
Правила деления и сдвигов описаны ниже. Поведение совпадает в интерпретаторе и машинном коде.

Второй операнд любой бинарной i32-операции может быть **литералом** (0.17):
`ADD r0 5`, `SUB r0 1`, `EQ r1 0`, `SHL r2 3`, `MUL r3 -7`, вплоть до
`-2147483648`; `MOV r0 42` работает как `LOAD`. Литерал — значение, а не регистр:
он не участвует в анализе инициализации и не расширяет регистровый файл
(`ADD r0 255` не читает `r255`). Деление на литеральный ноль и литеральный сдвиг
вне 0..31 — ошибки **компиляции** (`division by literal zero is certain to fail`,
`literal shift count must be in 0..31`), одинаковые в обоих бэкендах.

В исходном примере `RET reg1` нарушал требование трёх полей, а `r1, r2`
распадался на два поля. Исправленный формат: `RET r0 _` и `CALL add r1,r2`.

## Переменные и массивы (0.6)

Объявления `VAR` и `ARRAY` располагаются сразу после `GENE`, до первой команды или
метки. Между объявлениями допустимы пустые строки и комментарии. Начальное значение
переменной — десятичное i32; длина массива — положительная десятичная константа.
Имена локальны для функции: одинаковые имена в разных функциях разрешены.
В одной функции имя нельзя объявлять дважды; имена вида `rN` и `_` зарезервированы.
Имена функций и меток образуют отдельные пространства имён.

```text
GENE main i32/1
VAR saved 0
ARRAY items 4
SET saved r0
LOAD r1 2
ASET items r1,r0
AGET r2 items,r1
GET r0 saved
ADD r0 r2
RET r0 _
END _ _
```

При входе `7` результат — `14`. Все строки сохраняют три поля; запятые внутри
третьего поля пишутся без пробелов. `GET`/`SET` работают только с переменной,
`AGET`/`ASET`/`LEN` — только с массивом. Вычисления выполняются прежними командами
над регистрами. Индекс и записываемое значение читаются до записи результата:
например, `AGET r0 items,r0` разрешён, если `r0` уже инициализирован.

Массив индексируется от `0` до `LEN - 1`. Каждое чтение и запись проверяют индекс
**до обращения к памяти**, включая отрицательные значения. Например:

```powershell
.\codons.exe run examples\variables.dna 10
.\codons.exe run examples\array_sum.dna 2 3
.\codons.exe run examples\array_at.dna 7
.\codons.exe run examples\array_at.dna 8
.\codons.exe test examples\array_sum.dna examples\array_sum.csv
```

Первые три результата: `55`, `392`, `49`. Четвёртая команда сообщает файл, строку
и `array index 8 out of bounds: valid indices are 0..7 (length 8)`.
Ошибка завершает текущий запуск; `live` и `test` позволяют продолжить работу.

Каждый вызов получает свежие собственные данные: `VAR` — начальные числа,
`ARRAY` — нули. `PARAM` ссылается на данные вызывающей функции. Остальные данные
родителя сохраняются во время вложенных вызовов; данные
разных запусков и потоков независимы. Между запусками состояние не сохраняется.
Изменение локальных имён и размеров при `reload` разрешено; старый вызов завершает
работу со своими данными и своей версией программы.

До **64 объявлений** и **65 536 ячеек i32** суммарно на функцию (256 KiB).
Сверх объявлений кадр вмещает до **256 регистровых ячеек** (0.16): регистры живут
в том же кадре и учитываются в лимите цепочки вызовов, но не обнуляются и не
расходуют шаги — статический анализ гарантирует запись до чтения.
На одновременно активную цепочку вызовов — до **262 144 ячеек** (1 MiB локальных
данных). Лимиты проверяются до запуска. Последовательные вызовы переиспользуют
область памяти; их расходы на инициализацию суммируются в лимите шагов.
Это лимит данных языка, а не всей памяти процесса или компилятора.
Изменяемого размера и глобальных переменных нет. Передача массивов описана ниже.

## Структуры-сахар (0.16)

`STRUCT p x,y` в области объявлений (до первой команды или метки, как `VAR` и
`ARRAY`) раскрывается в обычные одноячеечные локали с точечными именами:
`p.x`, `p.y`. Каждое поле читается и записывается прежними `GET`/`SET`; само имя
`p` локалью не становится (`GET r0 p` — ошибка неизвестной локали). Дамп
нормализует объявление в строки `VAR p.x 0`, которые разбираются обратно без
изменений. Поля входят в лимит 64 объявлений и 65 536 ячеек. Никаких новых
опкодов, типов и влияния на ABI — это чистый сахар над локалями.

```text
GENE main i32
STRUCT point x,y
LOAD r1 40
LOAD r2 2
SET point.x r1
SET point.y r2
GET r3 point.x
GET r4 point.y
ADD r3 r4
RET r3 _
END _ _
```

Результат — `42`.

## Массивы в функциях (0.8)

Функция объявляет **один** входной массив через `PARAM items r0`. Объявление
стоит вместе с `VAR` и `ARRAY` до любых команд и меток. Имя `items` локально
для этой функции; оно не обязано совпадать с именем у вызывающего.
Нужна сигнатура `i32/1`…`i32/4`: первое число — длина, остальные, если есть, —
обычные аргументы (порог, множитель и т. п.). `main` получает данные через `ARRAY`/`READ`
и не может объявлять `PARAM`.

```text
GENE set_first i32/2
PARAM items r0
LOAD r2 0
JZ r0 done
ASET items r2,r1
LABEL done _
LEN r0 items
RET r0 _
END _ _

GENE main i32
ARRAY values 8
LOAD r3 4
LOAD r4 42
CALL set_first values,r3,r4
LOAD r1 0
AGET r0 values,r1
RET r0 _
END _ _
```

Результат — `42`. Функция получает первые четыре элемента исходного массива,
изменяет первый на месте; копирования и обнуления переданного массива нет.
`CALL` сохраняет остальные регистры родителя; результат по-прежнему возвращается в `r0`.

- Перед вызовом длина проверяется: `0 <= длина <= доступная длина массива`.
  Ошибка указывает строку `CALL`; слишком большая или отрицательная длина не обрезается.
- `LEN` для `PARAM` возвращает переданную длину. Она сохраняется на весь вызов:
  изменение `r0`, другой `CALL` или `READ` не меняют границу.
- `AGET`/`ASET` проверяют индекс относительно этой длины. `READ`/`WRITE` также
  ограничены этой частью. При длине ноль допустимы `LEN`, пустые `READ`/`WRITE`
  и передача дальше, но нет допустимых индексов.
- Массив можно передать дальше, сохранив или уменьшив доступную длину.
  Дочерняя функция не может расширить её до вместимости исходного массива.
  После возврата граница родителя остаётся прежней.
- `PARAM` входит в лимит 64 объявлений, но не выделяет ячеек и не расходует
  шаги на копирование или инициализацию. Сам `CALL` расходует один шаг;
  тело функции использует общий бюджет запуска.

Массив принадлежит объявившему его вызову и доступен дочерним функциям только во время
их выполнения. Вернуть или сохранить ссылку на него нельзя. Существующие сигнатуры
и скалярные вызовы продолжают работать. Наличие `PARAM` проверяется при связывании
вызовов и при `reload`; переименование параметра разрешено.

Пример цепочки из отдельных функций в `examples/list_pipeline.dna`:

```text
IMPORT lists.dna _
GENE main i32/1
ARRAY values 256
MOV r1 r0
READ values r0
CALL filter values,r0,r1
CALL sort values,r0
WRITE values r0
RET r0 _
END _ _
```

```powershell
.\codons.exe run examples\list_pipeline.dna 5 --input examples\numbers.txt --output pipeline.txt
```

На экран выводится `3`, в новый `pipeline.txt` записываются `7`, `7`, `12`.
Порог передаётся при запуске. Пустой результат сохраняется пустым файлом.
Пример вмещает до 256 чисел. `examples/lists.dna` содержит `filter` (сохраняет порядок),
`sort` (сортировка вставками по возрастанию) и `sum` (сумма с обычным переполнением i32).
Фильтр возвращает новое количество, сортировка — прежнее; остаток массива не очищается.
`sum` возвращает сумму, для пустой части — ноль. Модуль подключается через `IMPORT`.

## Списки чисел из файлов (0.7)

Входной файл содержит одно десятичное число i32 на строку. Пример `examples/numbers.txt`:

```text
7
-3
0
7
12
-9
4
```

Готовые программы суммируют, фильтруют и сортируют этот список:

```powershell
.\codons.exe run examples\list_sum.dna --input examples\numbers.txt
.\codons.exe run examples\list_filter.dna 5 --input examples\numbers.txt --output filtered.txt
.\codons.exe run examples\list_sort.dna --input examples\numbers.txt --output sorted.txt
```

Сумма — `18`. Фильтр сохраняет числа не меньше порога `5`: `7`, `7`, `12`,
а на экран возвращает количество `3`. Сортировка сохраняет `-9`, `-3`, `0`, `4`,
`7`, `7`, `12` по одному числу на строку и возвращает количество `7`.
Эталонные списки лежат в `examples/numbers_filtered.txt` и `examples/numbers_sorted.txt`.
Сумма и фильтр принимают до 4096 чисел, учебная сортировка вставками — до 256.
Обычное переполнение суммы по модулю 2³² сохраняется.

Минимальная программа копирования:

```text
GENE main i32
ARRAY items 1024
READ items r0
WRITE items r0
RET r0 _
END _ _
```

Правила команд:

- `READ` каждый раз копирует **весь тот же входной список** с начала массива.
  Список должен помещаться полностью, иначе возникает ошибка без обрезания.
  Остальные ячейки массива не изменяются. `r0` в примере становится длиной списка,
  а `LEN` по-прежнему возвращает вместимость массива — здесь `1024`.
- `WRITE` читает количество из регистра: разрешены значения от нуля до длины массива.
  Команда сохраняет снимок элементов; последующие изменения массива его не меняют.
  При нескольких `WRITE` **последний выполненный** задаёт весь выходной список.
- Все вложенные вызовы используют один входной и один выходной список запуска.
  Файловые операции внутри машинного кода не выполняются.
- Каждая команда расходует **1 шаг плюс число переносимых элементов**. Весь перенос
  проверяется на оставшийся бюджет до копирования. Пустой список расходует один шаг.
- Если достигнут `READ` без входного списка или `WRITE` без выходного — ошибка с файлом
  и строкой исходника. Неисполненная ветка с этими командами не требует файла.

Флаги `--input` и `--output` доступны для **`run` и `interpret`**, по одному каждого вида.
Они сочетаются с обычными входными числами и `--json`. Пути можно заключать в кавычки;
кириллица и пробелы поддерживаются. `check` и `dump` не требуют файлов данных.
В `test` пути списков задаются в CSV, а не флагами. Интерактивный `live` остаётся без файловых флагов.

Файл входа целиком проверяется до выполнения: UTF-8, необязательный BOM, LF/CRLF,
пустые строки и пробелы по краям допускаются. Пустой файл — список из нуля чисел.
Комментарии, запятые, дроби и другие форматы в списке не поддерживаются.
Лимиты: **1 MiB входного файла, 65 536 чисел, 511 байт на строку до LF**.
Ошибки содержат путь и, для повреждённой строки, её номер.

Выход записывается только после успешного выполнения, в UTF-8 без BOM, с LF.
Сначала полностью записывается временный файл рядом с результатом, затем он
переименовывается без замены существующего файла. Если путь уже занят, нужно выбрать
новый. При ошибке вычисления результат не создаётся. Если указан `--output`, но ни
один `WRITE` не выполнен, сообщается ошибка; для пустого результата нужен `WRITE`
со счётчиком ноль. Временные файлы удаляются при обработанных ошибках записи.

В stdout остаётся число из `RET`; сам список сохраняется в указанный файл.
Успех с `--output --json` дополнительно содержит `output` (путь) и `output_count`.
С флагом `--json` выходной список также возвращается прямо в ответе как
`output_list` — временный файл не нужен, `--output` можно не указывать; буфер
на 65536 элементов выделяется автоматически. В текстовом режиме без `--output`
программа с `WRITE` по-прежнему завершается ошибкой.
Ошибки чтения/сохранения имеют `stage: "file"`, ошибки операций — `stage: "run"`.
Ограничение шагов относится к вычислениям и переносу данных, а не к времени ожидания диска.

## Строки (0.12)

```text
GENE main i32
SLOAD r1 "hello"
SLOAD r2 " world"
SCAT r3 r1,r2
SLEN r4 r3
RET r4 _
END _ _
```

Результат — `11`. Строка — **неизменяемая последовательность байтов**; регистр хранит
не указатель, а хэндл (номер строки в таблице запуска). Подделать или испортить хэндл
нельзя: чужой или испорченный номер — это ошибка выполнения, а не обращение к памяти.

Литерал пишется в кавычках в поле операнда: `SLOAD r1 "text"`. Поддерживаются
экранирования `\n`, `\t`, `\\`, `\"` и `\xHH` (один произвольный байт, hex).
Кавычки защищают пробелы и `#`: внутри литерала они не делят поля и не начинают
комментарий. Команда `dump` печатает литералы обратно с экранированием, так что
дамп перечитывается байт-в-байт.

- `SLEN` возвращает число байтов; `SGET` — байт по индексу `0..LEN-1`.
- `SCAT` создаёт новую строку; операнды не меняются. Результат живёт до конца
  запуска; память внутри запуска не освобождается.
- `SEQ` сравнивает побайтово: длина, затем содержимое.
- Строки сравниваются и передаются только через хэндлы. Арифметика над хэндлом
  превращает его в обычное число; использовать такое число как хэндл позволено,
  но чужой номер даст ошибку `invalid string handle`.

Лимиты на программу: до **1024 литералов** и **256 KiB** их суммарных байтов.
Лимиты на один запуск: до **4096 строк** в таблице (литералы плюс результаты `SCAT`)
и **512 KiB** пула для результатов. `SCAT` расходует 1 шаг плюс по шагу за копируемый
байт, `SEQ` — 1 шаг плюс по шагу за сравниваемый байт; `SLOAD`, `SLEN`, `SGET`
расходуют один шаг. Все проверки делаются до обращения к памяти; ошибки
(`invalid string handle`, `string index … out of bounds`, `string handle table full`,
`string memory exhausted`) содержат файл и строку и совпадают в JIT и интерпретаторе.

Строки — это байты, а не текст: кодировки и ввод-вывод строк не определены.
Для обмена числовыми данными с файлами используются списки из 0.7.

## Печать и хост-возможности (0.13)

```text
GENE main i32
SLOAD r1 "hello\n"
PRINT r1 _
RET r1 _
END _ _
```

`PRINT` пишет байты строки в канал, который хост **явно выдал** этому запуску.
Программа без канала не может напечатать: она останавливается с ошибкой
`PRINT requires a host print capability` — это модель capabilities: язык не имеет
скрытых обращений к системе, каждый канал внешнего мира перечислен в `BioIO`
(входной список, выходной список, печать) и выдаётся хостом по решению.

Как выдаётся канал в готовом CLI:

| Команда | Канал печати |
|---|---|
| `run`, `interpret` (текст) | Байты идут в stdout прямо во время работы программы |
| `run`, `interpret --json` | Вывод накапливается и возвращается полем `"printed"` |
| `verify` | Печать обоих бэкендов должна совпасть побайтово; в текстовом режиме согласованные байты печатаются один раз |
| `test` (CSV) | Канал выдан, вывод отбрасывается: примеры сравнивают данные |
| `live` | stdout интерактивной сессии |

`PRINT` расходует один шаг плюс по шагу за байт; проверка бюджета происходит до
отправки, поэтому частичной записи не бывает. Ошибка обратного вызова хоста —
`the host print callback failed`. Встраиваемые приложения выдают канал через
поля `print` и `print_user` в `BioIO`; `bio_program_run` без `BioIO` печать
запрещает. Напечатанное — байты; перевод строки программа добавляет сама (`\n`).

## Деление, логика и биты

Два операнда читаются до записи результата в первый. Например, `DIV r0 r0`
для ненулевого входа даёт `1`, а `XOR r0 r0` — `0`. Второй операнд — регистр;
числовую константу сначала загрузите через `LOAD`. У `NOT` и `LNOT` третье поле
обязательно `_`; с `--repair` пропущенное третье поле у этих операций
восстанавливается, потому что оно не влияет на значение.

**Деление:** `DIV` округляет к нулю. `MOD` возвращает остаток со знаком делимого
или ноль: `-7 DIV 3 = -2`, `-7 MOD 3 = -1`; `7 MOD -3 = 1`.
Нулевой делитель в любой из этих операций — ошибка выполнения `division by zero`.
`-2147483648 DIV -1` даёт ошибку `division overflow`: ответ не помещается в i32.
`-2147483648 MOD -1` корректен и равен `0`.

**Логика:** ноль означает ложь, любое ненулевое число — истину; результат всегда
`0` или `1`. `LAND`, `LOR`, `LXOR` читают оба регистра, поэтому оба должны быть
инициализированы. Эти операции не пропускают другие инструкции: для условного
выполнения используются переходы. Пример различия: `8 AND 2 = 0`, `8 LAND 2 = 1`.
`NOT 0` инвертирует биты и даёт `-1`, `LNOT 0` даёт логическую единицу.

**Сдвиги:** число бит должно быть от `0` до `31`, иначе возникает ошибка
`shift count must be in 0..31`. Значение не маскируется и не исправляется автоматически.
`SHL` отбрасывает биты, вышедшие за 32 разряда. `SHR` заполняет старшие биты нулями,
`SAR` — знаковым битом: `-8 SHR 1 = 2147483644`, `-8 SAR 1 = -4`.
Сдвиг на ноль оставляет значение прежним; результат любого сдвига выводится как i32.

Каждая новая операция расходует один шаг. Лимит проверяется перед самой операцией;
если он уже исчерпан, сообщается ошибка лимита. При арифметической ошибке
частичный результат не возвращается, вложенные вызовы завершаются с той же ошибкой.
В `live` доступен следующий запуск, а `test` продолжает остальные CSV-примеры.
`check` проверяет структуру программы; ошибки значений обнаруживаются при выполнении
соответствующей операции. Пропущенная переходом ветка не вызывает ошибку выполнения.

Готовые примеры:

```powershell
.\build\codons.exe run examples\divide.dna -7 3
.\build\codons.exe run examples\remainder.dna -7 3
.\build\codons.exe run examples\logic.dna 8 2
.\build\codons.exe run examples\flags.dna 8 2
.\build\codons.exe run examples\bits.dna -1
.\build\codons.exe test examples\divide.dna examples\divide.csv
.\build\codons.exe test examples\bits.dna examples\bits.csv
```

Первые пять команд возвращают `-2`, `-1`, `1`, `0`, `32`.
`bits.dna` подсчитывает единичные биты в полном 32-битном представлении числа.

## Ветвления и циклы

Сумма чисел от 1 до входного `n` (`examples/sum.dna`):

```text
GENE main i32/1
LOAD r1 0
MAX r0 r1
LOAD r2 1
LABEL loop _
JZ r0 done
ADD r1 r0
SUB r0 r2
JMP loop _
LABEL done _
RET r1 _
END _ _
```

`run examples/sum.dna 10` возвращает `55`; для нуля и отрицательных входов — `0`.
Обратный переход создаёт цикл. Для условия используйте `EQ` или `LT`, затем
`JZ`/`JNZ`; любое ненулевое значение, включая отрицательное, считается истинным.

Метки можно объявлять до или после перехода. Они видны только внутри своей
функции: одинаковое имя в разных функциях разрешено, дубликат внутри одной — ошибка.
За `RET` другую ветку нужно начинать с `LABEL`. Достижимый путь не может
провалиться в `END`: он должен вернуть значение или продолжить выполнение переходом.

Проверка рассматривает обе стороны условного перехода, без вычисления констант.
Если цикл может выполниться ноль раз, нужные после него регистры следует заполнить
до цикла. Неинициализированный регистр, неизвестная метка или переход в другую
функцию отклоняются с указанием файла и строки.

На один запуск выделяется **1 000 000 шагов**, совместно для `main` и всех его вызовов.
`LABEL`, `GENE`, `END`, `IMPORT`, `VAR`, `ARRAY`, `PARAM` и `STRUCT` как узлы не
расходуют шаги; `CALL`, переходы, операции с данными и `RET` расходуют один шаг.
Инициализация при входе в функцию дополнительно расходует один шаг на каждую
**объявленную** ячейку i32: переменная — один, массив из 16 элементов — 16.
Регистры шагов не расходуют (0.16): они не обнуляются, потому что статический
анализ гарантирует запись до чтения. Это относится и к неиспользуемым
объявлениям в вызванной функции. Ошибка во время инициализации указывает на строку `GENE`.
Ровно миллион разрешён, попытка следующего шага завершает запуск ошибкой
`execution budget exhausted` с указанием строки. Частичный результат не возвращается.
Следующий запуск получает новый лимит, параллельные запуски имеют отдельные счётчики.
Это одинаково работает в `run`, `interpret` и `live`.

Для проверки защиты: `run examples/infinite.dna`. Приложение сообщит об исчерпании
лимита. В `live` после такой ошибки можно продолжать вводить команды или обновить код.
`check` проверяет структуру программы, но не доказывает завершение цикла.
Большое конечное вычисление тоже может исчерпать лимит.

## Рекурсия (0.14)

Функция может вызывать себя прямо (`fact` вызывает `fact`) или по кругу
(`even`/`odd`). Ограничения перенесены из компиляции во время выполнения и
проверяются **перед** выделением кадра:

- не больше **256 одновременно активных генов** (`call depth limit reached`);
- не больше **262 144 ячеек i32** локальных данных во всех активных кадрах вместе
  (`call frame memory exhausted: need N more cells, M left this run`).

Оба сообщения содержат файл и строку `CALL` и побайтово совпадают в JIT и
интерпретаторе. Каждый уровень получает полностью свежий кадр: объявленные
локали, массивы и — с 0.16 — весь регистровый файл `r0`…`r255`. Для программ
без циклов в графе вызовов статический учёт шагов и памяти остаётся точным;
программы с циклом получают `dynamic_steps: true` в JSON и контролируются
только пределами выполнения.

```text
GENE fact i32/1
LOAD r1 1
JZ r0 base
MOV r2 r0
SUB r0 r1
CALL fact r0
MUL r2 r0
MOV r0 r2
RET r0 _
LABEL base _
LOAD r0 1
RET r0 _
END _ _
GENE main i32/1
CALL fact r0
RET r0 _
END _ _
```

`run examples\factorial.dna 5` возвращает `120`.

## Широкие регистры i64 (0.15)

Рядом с 32-битными регистрами существует отдельный класс `w0`…`w3` для
64-битной арифметики. Неявных преобразований нет: пересечение классов только
через `WIDEN wN rM` (знаковое расширение i32 → i64) и `NARROW rN wM`
(ошибка `wide value does not fit in i32`, если значение не помещается).
Сравнения `WEQ`/`WLT` пишут флаг 0/1 в обычный регистр — ветвления остаются
32-битными. Широкие регистры локальны для кадра вызова и не передаются
аргументами: граница вызова по-прежнему оперирует только i32.

- `WLOAD wN value` принимает полный диапазон i64, включая `-9223372036854775808`.
- `WADD`/`WSUB`/`WMUL` заворачиваются по модулю 2⁶⁴; битовые `WAND`/`WOR`/`WXOR`/`WNOT`.
- `WDIV`/`WMOD` знаковые с усечением к нулю; деление на ноль — `division by zero`,
  а пара `INT64_MIN / -1` — `division overflow`.
- `WSHL`/`WSHR`/`WSAR` требуют счётчик `0..63`, иначе `wide shift count must be in 0..63`.
- Инициализация широких регистров проверяется тем же анализом:
  `read of uninitialized wide register wN`.

Все ошибки выполнения содержат файл и строку и совпадают в JIT и интерпретаторе.
Пример `examples/fib64.dna` вычисляет 90-е число Фибоначчи (не помещается в i32)
и сверяет его с константой через `WEQ`:

```powershell
.\build\codons.exe run examples\fib64.dna 90
.\build\codons.exe test examples\fib64.dna examples\fib64.csv
```

Результат — `1` (совпадение). `examples/mix4.dna` показывает `main i32/4`
с четырьмя входными числами: `run examples\mix4.dna 15 0 10 100` → `110`.

## Проверка по CSV-примерам

```powershell
.\build\codons.exe test examples\sum.dna examples\sum.csv
.\build\codons.exe test examples\price.dna examples\price.csv --json
```

CSV для суммы (`examples/sum.csv`):

```csv
arg1,expected
10,55
0,0
-5,0
100,5050
```

Заголовок обязателен и зависит от числа аргументов `main`:

| Входы | Заголовок | Пример строки |
|---|---|---|
| 0 | `expected` | `30` |
| 1 | `arg1,expected` | `10,55` |
| 2 | `arg1,arg2,expected` | `3,250,750` |
| 3 | `arg1,arg2,arg3,expected` | `1,2,3,6` |
| 4 | `arg1,arg2,arg3,arg4,expected` | `1,2,3,4,10` |

Имена столбцов и их порядок фиксированы. `arg1` поступает в `r0`, `arg2` — в `r1` и т. д.;
`expected` — ожидаемое знаковое i32. Все числа десятичные, от −2147483648 до
2147483647. Учитывайте правила операций: сложение, вычитание и умножение
переполняются по модулю 2³², переполнение деления считается ошибкой.

Формат файла: UTF-8, разделитель — **запятая**. Поддерживаются BOM, LF/CRLF,
последняя строка без перевода строки, пустые строки, пробелы и табуляция вокруг
значений, а также ячейки в двойных кавычках (`"10","55"`). В каждой непустой строке
один пример. Комментарии, многострочные ячейки и кавычки внутри значения
не поддерживаются. При экспорте из таблицы выбирайте UTF-8 и запятую, а не `;`.

Программа компилируется один раз. Весь CSV проверяется **до выполнения примеров**:
неверный заголовок, пустая ячейка, лишний столбец или недопустимое число завершают
команду с понятной ошибкой. Пустой набор не считается успешной проверкой.
Пути `.dna` и CSV задаются относительно текущей папки; имена с пробелами берите
в кавычки. Файлы не изменяются.

Для каждого примера выводятся строка CSV, входы, ожидаемый ответ и:

- `PASS` — фактический ответ совпал;
- `FAIL` — ответ отличается; показаны `expected` и `actual`;
- `ERROR` — выполнение завершилось ошибкой; показана причина и строка `.dna`.

После `FAIL` или `ERROR` выполняются остальные примеры. Каждый получает свой лимит
в 1 000 000 шагов; вложенные вызовы используют тот же лимит. Набор ограничен
1000 примерами, 1 MiB файла и 511 байтами на физическую строку до LF.
В итогах `failed` включает и несовпадения (`mismatches`), и ошибки исполнения (`errors`).
Код завершения `0` означает, что прошли все примеры; `1` — несовпадение, ошибка
исполнения, компиляции или CSV; `2` — неверная команда/аргументы.

`--json` возвращает один объект с `file` (путь CSV), массивом `cases`, `ok` и `summary`.
Каждый элемент `cases` содержит `line`, `inputs`, `expected`, `status`
(`passed`, `failed` или `error`), а также `actual` либо `error: {stage, message}`.
При ошибке исполнения `actual` отсутствует, чтобы не подменять ошибку числом.
`summary` содержит `total`, `passed`, `failed`, `mismatches`, `errors`.

Если CSV не удалось прочитать или разобрать, вместо результатов возвращается
`ok: false` и `error: {stage: "csv", code, file, line, column, message}`.
`line` и `column` считаются с единицы; `column` — номер столбца CSV, а не символа;
ноль означает, что конкретная строка или столбец не применимы.
Коды CSV-ошибок: `open`, `read`, `memory`, `encoding`, `file_limit`, `line_limit`,
`case_limit`, `header`, `column_count`, `quotes`, `integer`, `empty`.
При ошибке CSV полей `cases` и `summary` нет. Ошибки `.dna` и аргументов
сохраняют обычные форматы `compile` и `arguments`.

Готовые наборы: `main.csv`, `sum.csv`, `price.csv`, `factorial.csv`, `divide.csv`,
`remainder.csv`, `bits.csv`, `flags.csv`, `logic.csv` рядом с одноимёнными
`.dna`. `--repair` разрешён для исправления пропущенных `_` в `.dna`, как и в `run`.
Проверка подтверждает результат только на заданных входах. Команда `test`
самостоятельна и не меняет поведение `reload`.

## Проверка списков по CSV (0.9)

```powershell
.\codons.exe test examples\list_pipeline.dna examples\list_pipeline.csv
```

Ожидаемый итог: `Tests: 8 total, 8 passed, 0 failed`. Набор проверяет обычный список,
пустой вход, повторы, отрицательные числа, отбор всех/ни одного элемента,
крайние i32 и одиночное число. Все файлы входят в переносимый архив.

Новый заголовок зависит от числовых аргументов `main`:

| Аргументы main | Заголовок CSV |
|---|---|
| 0 | `input,expected,expected_output` |
| 1 | `arg1,input,expected,expected_output` |
| 2 | `arg1,arg2,input,expected,expected_output` |
| 3 | `arg1,arg2,arg3,input,expected,expected_output` |
| 4 | `arg1,arg2,arg3,arg4,input,expected,expected_output` |

Пример для фильтра и сортировки с одним аргументом — порогом:

```csv
arg1,input,expected,expected_output
5,numbers.txt,3,numbers_filtered.txt
2147483647,numbers.txt,0,list_cases/empty.txt
```

`input` — путь к исходному списку, `expected` — ожидаемое число из `RET`,
`expected_output` — путь к эталонному списку. Оба пути обязательны; пустой список
задаётся пустым файлом. В одном CSV используется один из двух форматов: прежний
числовой или новый со списками. Старые наборы и их отчёты продолжают работать.

Относительные пути списков считаются **от папки CSV**, независимо от папки программы
и текущей папки запуска. Абсолютные пути тоже допустимы. Пробелы и кириллица поддерживаются;
путь с запятой заключите в двойные кавычки. Пробелы по краям ячейки удаляются.
Переносы строк и экранированные кавычки внутри ячейки не поддерживаются.

Списки читаются тем же способом, что `--input`: UTF-8, необязательный BOM,
LF/CRLF, одно десятичное i32 на непустой строке. Числа сравниваются по значениям,
поэтому `+7` и `7`, разные переводы строк и пустые строки не создают различий.
На каждый файл действуют прежние лимиты: 1 MiB, 65536 чисел, 511 байт на строку до LF.
CSV ограничен 1000 примерами, 1 MiB и 511 байтами на физическую строку.

**PASS** требует совпадения числа из `RET`, длины, порядка и всех элементов списка.
**FAIL** означает различие числа или списка. Показаны длины и первое различие,
номер элемента считается с единицы:

```text
FAIL cases.csv:2: inputs=[5] expected=3 actual=3; output_count: expected=3 actual=3; element 2: expected=12 actual=7
```

При лишнем/пропущенном элементе соответствующая сторона помечена `<missing>`.
Сначала ищется различие в общей части, затем первый лишний/пропущенный элемент.
Если отличается только число `RET`, список может оставаться совпавшим.

**ERROR** означает ошибку чтения списка или выполнения. Отсутствие `WRITE` —
тоже ошибка: для пустого результата программа должна выполнить `WRITE` с нулём.
Неверная длина, выход за границы и лимит шагов сохраняют обычную диагностику `.dna`.
После FAIL/ERROR проверяются остальные строки, каждый запуск получает новый бюджет.

CSV целиком проверяется **до запуска первого примера**. Файлы списков читаются
перед своим примером; оба файла должны успешно прочитаться до начала вычислений.
Ошибка в файле относится к этой строке CSV и не останавливает остальные примеры.
Отчёт указывает вход или эталон, путь и, если применимо, строку файла списка.

Команда **не создаёт выходные файлы и не изменяет входы или эталоны**. `WRITE`
попадает в память через `BioIO`, после успешного вызова сравнивается последний снимок.
Результаты всех примеров не накапливаются: буферы списков освобождаются после каждого.
Собственные данные функций и контекст выполнения создаются заново для каждого запуска.

JSON сохраняет прежние `summary`, статусы и коды завершения. Строки файлового CSV
добавляют `input` и `expected_output` с путями из ячеек. При успешном выполнении
появляется `output`, даже если сравнение выявило FAIL:

```json
"output": {
  "matched": false,
  "expected_count": 3,
  "actual_count": 2,
  "difference": {"element": 3, "expected": 12, "actual": null}
}
```

`difference` отсутствует при полном совпадении списков, `null` означает отсутствие
элемента на соответствующей стороне. `output.matched` относится только к списку;
общий статус учитывает и `RET`. При ERROR поля `actual` и `output` отсутствуют.
Ошибка файла имеет `error.stage: "file"`, `field: "input"` или `"expected_output"`,
`file` и `message`. Ошибка выполнения имеет `stage: "run"`. Номер строки CSV
находится в `case.line`; строка повреждённого списка — в сообщении.
Пустая ячейка пути отклоняется ещё при разборе CSV с `stage: "csv", code: "path"`.

## Команды

```powershell
.\build\codons.exe check .\examples\main.dna
.\build\codons.exe dump .\examples\main.dna
.\build\codons.exe interpret .\examples\main.dna
.\build\codons.exe verify .\examples\sum.dna 10
.\build\codons.exe emit .\examples\main.dna .\work\main.bin
.\build\codons.exe run .\examples\repairable.dna --repair
.\build\codons.exe test .\examples\price.dna --init
.\build\codons.exe fix .\examples\repairable.dna
```

`check` разбирает и проверяет программу без запуска и без выделения исполняемой
памяти. `interpret` выполняет тот же проверенный граф без JIT.
`verify` выполняет программу **в JIT и в интерпретаторе** и требует полного
совпадения: результата, выходного списка из `WRITE` либо одинаковой ошибки с тем же
файлом и строкой. Число печатается как в `run`, а строка `verified: JIT and
interpreter agree` идёт в stderr. При расхождении печатаются оба исхода, код
завершения — `1`. Совпадающая ошибка программы (например, выход за границы) —
тоже согласие бэкендов; код завершения при этом `1`, как у `run`. Поддерживаются
`--input`, `--output`, `--repair` и `--json` с полем `verified`.
`dump` выводит нормализованный `.dna`: импорты развёрнуты, операнды читаемы,
результат можно сохранить как исходник и снова запустить.
`emit` сохраняет сырые байты функций, без PE-заголовка и метаданных раскрутки стека;
это **не самостоятельный `.exe`**. Команда `emit` сообщает смещение `main`,
которое может быть не нулевым.
Машинный код требует внутреннего контекста лимита шагов и области локальных данных;
для встраивания используйте C API, описанный ниже.

Для вызова из другого приложения добавьте `--json`:

```powershell
.\build\codons.exe run .\examples\price.dna 3 250 --json
.\build\codons.exe check .\examples\price.dna --json
```

В stdout приходит один JSON-объект. Успех содержит `ok: true`, результат в `result`
для выполнения и `stats` с параметрами программы. Ошибка содержит `ok: false` и
`error: {stage, message}`. `stage` — `arguments`, `compile`, `run` или `file`.
Для `test` формат отчёта и CSV-ошибок описан выше.
При `new --json` успешный ответ содержит `file`.
`stats.execution_limit` равен `1000000`. Для программы с достижимыми переходами или `READ`/`WRITE`
`dynamic_steps` равен `true`, а `execution_steps` — `null`: число шагов заранее
не вычислено. Для линейной программы без операций со списками `execution_steps` содержит число шагов
до нормального возврата; ошибка выполнения может остановить её раньше.
Это оценка перед запуском, а не счётчик уже выполненных шагов.
`--json` не применяется к интерактивному `live` и текстовому `dump`.

## Инструменты для кодогенерации (0.17)

Язык целится в цикл «модель пишет — компилятор проверяет», поэтому интерфейс
ошибок сделан машинным:

- **Ошибки-подсказки.** Сообщения компилятора объясняют, как чинить:
  `expected exactly 3 fields; found 4: never put a space after a comma
  (write r1,r2)`, `read of uninitialized register r1 on a reachable path
  (write it before this point on every path, e.g. LOAD r1 0 ...)`,
  `undefined gene: f (declare it: GENE f i32/N ... END _ _, or fix the name)`.
- **`line_text` в JSON.** У каждой ошибки с локацией JSON-ответ несёт исходную
  строку сбоя — модель видит, что именно она написала, без повторного чтения
  файла. Повреждённая (не-UTF-8) строка не попадает в ответ, JSON остаётся
  валидным.
- **`test --init [out.csv]`.** Печатает (или пишет в новый файл) точный
  CSV-заголовок для `main`: арность и каналы READ/WRITE выводятся из программы
  (`bio_program_channels` в C API). Ручной подбор колонок больше не нужен.
- **`fix <file.dna> [out.dna]`.** Применяет `--repair` и записывает
  нормализованную программу в новый файл (по умолчанию `<имя>.fixed.dna`);
  существующие файлы не перезаписываются, сам исходник не трогается.
- **[LLM.md](LLM.md).** Машинный справочник: грамматика, семантика опкодов с
  условиями сбоев, десять проверенных идиом, таблица «ошибка → исправление».
  Предназначен для включения в системный промпт.
- **Харнес [tests/llm_eval/](tests/llm_eval/).** 16 задач с эталонными
  решениями; раннер `llm_eval.py` прогоняет каталог кандидатов и раскладывает
  неудачи по классам (`field-count`, `uninitialized`, `undefined-name`, …),
  чтобы изменения языка и промпта измерялись, а не угадывались. Эталоны
  охраняются сьютом `llm_eval_selftest`.
Коды завершения: `0` — успех, `1` — ошибка программы/файла, `2` — неверная команда
или входные аргументы. Возвращённое программой число печатается в ответ, а не
используется в качестве кода завершения процесса.

## Горячее обновление

```powershell
.\build\codons.exe live .\examples\main.dna
```

Введите в этом же процессе:

```text
run
reload examples/updated.dna
run
reload examples/broken.dna
run
quit
```

Результаты: `30`, затем `42`. Ошибочный `broken.dna` отклоняется, следующий `run`
по-прежнему возвращает `42`. Пути команды `reload` считаются от текущего каталога;
пути `IMPORT` — от каталога импортирующего файла.
Для функции с параметрами в интерактивном режиме используйте `run 10 20`.

Новая программа проходит весь конвейер в отдельном объекте и отдельной памяти.
Публикация заменяет указатель под короткой блокировкой SRWLOCK. Каждый активный вызов
удерживает ссылку на свою версию, включая все вложенные вызовы. Старые код, граф и
таблица раскрутки стека освобождаются после последнего пользователя этой версии.
Компиляция не удерживает блокировку публикации.

### Шлюз по тестам (0.11)

```text
reload examples/price.dna --gate examples/price.csv
```

Кандидат компилируется, затем прогоняется по CSV-примерам **до публикации**.
Новая версия заменяет активную, только если все примеры зелёные; отчёт о примерах
печатается как в команде `test`. При красном CSV, битом файле примеров или
несовместимой сигнатуре активной остаётся прежняя версия. Тот же сценарий доступен
встраиваемым приложениям через C API: скомпилировать `bio_compile`, проверить
самостоятельно и опубликовать `bio_runtime_publish`.

При обновлении все ранее объявленные функции должны остаться с прежними именами
и числом числовых аргументов, а также наличием `PARAM`; добавлять новые можно. Проверяется и неиспользуемая часть
программы. Это простой консервативный контракт первой версии.

Обновление не перезапускает процесс. Оно **не является lock-free** и не обещает
нулевую задержку каждого запроса. В v0.10 заменяется полный снимок программы;
частичные патчи функций, миграция состояния и сетевой сервер пока не реализованы.

## Что означает DNA-Repair в этой версии

По умолчанию разбор строгий. Явный `--repair` имеет два безопасных действия:

- восстанавливает только неиспользуемое третье поле `_` у `RET`, `END`, `NOT`,
  `LNOT`, `WNOT`, `LABEL`, `JMP` и `IMPORT`;
- заменяет неоднозначный кодон на `QUARANTINE _ _`. Это относится к неполному
  триплету внутри функции, неверным операндам, неизвестной функции или метке,
  неправильному виду локальной переменной, чтению неинициализированного регистра
  и достижимому концу функции без `RET` или `JMP`.

Карантин не подставляет нули, не выбирает цель перехода и не продолжает повреждённое
вычисление. Если поток выполнения дошёл до него, `run` и `interpret` завершаются
с ошибкой `quarantined repaired codon reached` и исходной строкой. Неповреждённые
ветки продолжают работать. Файлы на диске не переписываются.

`check file.dna --repair --json` содержит `stats.repairs`,
`stats.quarantines` и `repair_log` с `file`, `line`, `kind`, `detail`.
Топологические ошибки вне тела функции — например повреждённый `GENE`, импорт,
кодировка или исчерпание лимита ресурсов — остаются ошибками компиляции.

## Ограничения и проверки

Поддерживаются i32 и i64 (отдельные регистры `w0..w3`), прямые вызовы и
локальные переходы. JIT-бэкенд — только Windows x64; сборка `-DCODONS_NO_JIT=ON`
переносима (C11 + POSIX-файловые операции) и проверяется в CI на Ubuntu и macOS
тем же набором тестов (CLI, дифференциальный фаззер, llm_eval, оракул). Команда
`emit-wasm` работает и в переносимой сборке: она генерирует C и вызывает clang
(переменная `CODONS_CLANG` или `clang` из PATH), см. `docs/wasm.md`. На функцию — до 256 регистров `r0`…`r255`
и до 64 объявлений локалей (0.16). Рекурсия ограничена 256 активными кадрами
и 1 MiB локальных данных (0.14). Нет указателей, FFI, макросов, выделения памяти
из DNA, полноценной системы типов, оптимизатора и генератора самостоятельного
PE-файла.
Пути и сообщения C API имеют кодировку UTF-8; на Windows файловые операции
выполняются через Unicode API. Русские имена файлов и папок поддерживаются.
В пути внутри `IMPORT` не допускаются пробелы: `IMPORT` принимает путь без кавычек,
а строковые литералы определены только для `SLOAD`.

Лимиты: 65 536 узлов, 256 функций, 512 уникальных имён целей вызова, меток и
локальных данных, 64 файла, 16 вложенных импортов, до 256 регистров на функцию,
4 MiB прочитанных исходников,
511 байт на физическую строку до LF; полный путь — до 1023 байт в UTF-8.
Строки: 1024 литерала и 256 KiB литеральных байтов на программу; 4096 хэндлов
и 512 KiB пула на запуск.
Это ограничивает ресурсы компиляции. Лимит исполнения проверяется перед каждым
выполняемым кодоном как в JIT, так и в интерпретаторе.
Для линейного графа вызовов сохранён предварительный расчёт: программа,
заведомо превышающая миллион шагов, отклоняется ещё до запуска.
Это ограничение объёма работы, не обещание определённого времени в миллисекундах.
Runtime предназначен для доверенного локального кода; изоляции процесса и песочницы нет.

Тесты ядра сравнивают 250 воспроизводимо сгенерированных программ сразу с JIT,
интерпретатором и независимо вычисленным результатом; отдельные CLI-тесты на
стандартном Python покрывают создание файлов, входные данные, JSON, Unicode,
нормализацию и обновления. Успешные тесты подтверждают проверенные сценарии,
а не отсутствие всех ошибок. Полная история тестового покрытия по версиям —
в [TESTING.md](TESTING.md).

## Для встраивания на C

В 0.2 изменён экспериментальный API выполнения: теперь функции возвращают статус,
а вычисленное число записывают по переданному указателю. Пример:

```c
BioError error = {{0}};
BioProgram *program = bio_compile("examples/price.dna", 0, &error);
int32_t arguments[2] = {3, 250};
int32_t result;
if (program) {
    if (bio_program_run(program, arguments, 2, &result, &error)) {
        /* result == 750 */
    }
    bio_program_release(program);
}
```

`bio_load` выполняет разбор и проверку без JIT; для него доступен
`bio_program_interpret`. `bio_compile` дополнительно готовит нативное выполнение.
`bio_runtime_run` принимает такие же аргументы и возвращает статус.
При ошибке выходное число остаётся неизменным. C API версии 0.1 нужно адаптировать;
существующие `.dna` без входных параметров продолжают работать.
Сигнатуры функций выполнения из 0.2 сохранены. В `BioStats` добавлено поле
`dynamic_steps`; при ненулевом значении `execution_steps` неизвестно и равно нулю
(в JSON — `null`). Приложения, использующие C API, нужно пересобрать с новым заголовком:
двоичная совместимость экспериментального API между версиями не гарантируется.

В 0.10 `BioStats` содержит `repairs` и `quarantines`, а
`bio_program_repair_count` / `bio_program_repair_at` позволяют C-хосту прочитать
файл, строку, тип и причину каждого ремонта. Указатели строк в `BioRepair` живут
до `bio_program_release`.

В 0.7 добавлены `bio_program_run_io`, `bio_program_interpret_io` и `bio_runtime_run_io`.
Они принимают `BioIO *` перед указателем результата. Старые функции продолжают
работать без каналов списков. Пример подготовки данных (при уже скомпилированном `program`):

```c
int32_t input[] = {7, -3, 12};
int32_t output[16];
BioIO io = {input, 3, output, 16, 0, 0};
int32_t result;
BioError error = {{0}};
if (bio_program_run_io(program, NULL, 0, &io, &result, &error)) {
    /* io.output_written distinguishes no WRITE from WRITE of an empty list. */
    /* io.output_count elements are valid when io.output_written is nonzero. */
}
```

`NULL` в `input`/`output` означает отсутствие канала; для доступного пустого канала
нужен ненулевой указатель с нулевым количеством/вместимостью. Максимум — `BIO_LIST_LIMIT`.
Входные элементы не меняются во время вычисления. Записи накапливаются в отдельном
буфере; при ошибке выходной массив, `output_count`, `output_written` и `result`
остаются прежними. После успеха без `WRITE` оба поля равны нулю.
Разные параллельные вызовы используют отдельные `BioIO` и выходные массивы.
