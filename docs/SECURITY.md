# Модель угроз песочницы Codons

> Документ описывает модель угроз и механизмы изоляции виртуальной машины Codons
> (самодостаточный мини-язык C11 + ВМ), предназначенной для безопасной компиляции и
> исполнения недоверенных / LLM-сгенерированных программ. Все утверждения привязаны
> к исходному коду ссылками `file:line`. Документ носит декларативный характер и не
> изменяет код; это рекомендательный артефакт для аудита и доработки.

---

## 1. Область действия и модель доверия

### 1.1. Что мы защищаем и от кого

| Субъект | Роль |
| --- | --- |
| **Злоумышленник** | Автор недоверенной программы или источник LLM-вывода, который порождает входной исходный текст Codons. |
| **Защищаемые объекты** | Хост-машина (ОС, её память и процессы), файловая система хоста, сеть хоста, другие процессы ОС, а также целостность самой ВМ (её память, таблицы строк, стек, внутренние структуры). |

Модель строится на принципе «программа не доверяет хозяину и хозяин не доверяет
программе»: недоверенный код исполняется в замкнутом адресном пространстве ВМ, а
вся связь с хостом идёт через ограниченный набор точек входа, каждая из которых
проверяет аргументы, размеры и бюджет.

### 1.2. Границы и стадии пайплайна

Код проходит следующие стадии, и на каждой есть свои риски и защитные механизмы:

```
источник (файл / байты)
   → лексер / парсер        (text → AST: CodonNode)
   → анализатор / таблица символов
   → бэкенд (интерпретатор runtime.c | JIT jit_win64.c)
   → среда выполнения (core.c)
   → хост-интерфейс ввода/вывода (BioIo / cli_io.c)
```

Хост-взаимодействие ограничено тремя каналами, перечисленными ниже; ни один из них
не даёт произвольного доступа к хост-ресурсам:

- **`READ`** — чтение только из массива входных байтов, переданных вызывающей
  стороной (`BioIO.input`); ВМ не открывает файлы сама.
- **`WRITE`** — запись только в буфер вывода, переданный вызывающей стороной
  (`BioIO.output`); ВМ не пишет в файлы/сеть сама.
- **`PRINT`** — обратный вызов `print`, который заряжает бюджет и может отсутствовать
  (тогда печать запрещена).

Прямой доступ к хост-файловой системе имеют только хосты командной строки
(`cli_io.c`) и только через явные списки имён файлов `--input` / `--output`
(`cli_read_list` / `cli_write_list`), — но это уровень хоста, а не ВМ.

### 1.3. Что вне модели

- Физическая безопасность, side-channel-атаки по времени/энергопотреблению.
- Злонамеренная или ошибочная реализация самого языка C11, на котором написана ВМ
  (компилятор, стандартная библиотека).
- Атаки на сам компилятор Codons вне сценария «скомпилировать и выполнить
  недоверенную программу».
- Гарантии корректности JIT-машинного кода против произвольного дампа/гонки потоков
  (см. раздел 5).

## 2. Активы и свойства безопасности

| Актив | Целостность | Доступность | Конфиденциальность |
| --- | --- | --- | --- |
| Память ВМ (`BIO_MEMORY_CELLS`) | границы массивов/строк проверяются (core.c 446, 553) | лимит объёма 262144 ячейки | память не совместно используема в пределах одного контекста |
| Таблица строк | STRING_TABLE/STRING_HANDLE (core.c 570, 538) | лимит 4096 строк / 512 KiB | — |
| Стек вызовов | DEPTH ≤ 256 (core.c 519), FRAME (523) | глубина ограничена | — |
| Бюджет исполнения | decrement на инструкцию (core.c 406) | `BIO_EXECUTION_LIMIT` = 1 000 000 шагов | — |
| Диапазоны целых | DIV_OVERFLOW / NARROW / WSHIFT (core.c 464, 655, 631) | — | — |
| Хост-ФС | READ/WRITE только через списки (cli_io.c) | — | имена файлов из белого списка, не из программы |
| Хост-сеть | недоступна из ВМ (нет FFI/syscall) | — | — |

Ключевые свойства: **целостность** (нет записи произвольной памяти), **доступность**
(ни одна программа не может занять ВМ или хост бесконечно), **конфиденциальность**
(программа не может прочитать произвольные файлы/сеть хоста — только переданные ей
входные байты).

## 3. Механизмы изоляции и лимиты (проверено по коду)

### 3.1. Отсутствие системных вызовов и FFI

ВМ не содержит сгенерированных системных вызовов и не загружает внешний код. Единственные
хостовые операции — обратные вызовы через структуру `BioIO`: `READ`/`WRITE` работают с
байтами, которые передал вызывающий (`cli_io.c`), а `PRINT` идёт через общий хелпер
`bio_print_helper` (core.c 358). Программа ВМ не может вызвать `open`/`exec`/сеть напрямую —
для этого закрыт сам набор опкодов; наблюдаемые опкоды в интерпретаторе (core.c 640–665)
это только арифметика/память/управление, а `OP_QUARANTINE` явно порождает fault (core.c 661).

### 3.2. Бюджет инструкций и общего времени

- Константа бюджета: `BIO_EXECUTION_LIMIT 1000000u` → **1 000 000 шагов**
  (`include/bio.h:9`).
- Инициализация счётчика в начале исполнения: `execution.remaining = BIO_EXECUTION_LIMIT`
  (core.c 692).
- Декремент на исполняемую инструкцию: `execution->remaining--` (core.c 406); при нулевом
  входе в цикл — `BIO_FAULT_BUDGET` (core.c 395).
- Печать заряжается тем же бюджетом: полный размер строки проверяется до выдачи —
  `execution->remaining < s->length` → `BIO_FAULT_BUDGET` (core.c 370–372).

**Важно:** бюджет начисляется только за исполняемые пользовательские операции; команды
меток/переменных/массивов/параметров могут не декрементировать счётчик (см. раздел 5.4).

### 3.3. Числовые предохранители и переполнения

- **Дел/мод на ноль**: `BIO_FAULT_DIV_ZERO` (core.c 462).
- **Переполнение деления (INT32_MIN / -1)**: обнаруживается честным 64-битным
  вычислением, результат зажимается в `INT32_MAX` → `BIO_FAULT_DIV_OVERFLOW` (core.c 464).
- **Сдвиг**: количество проверяется (`> 31` для 32-бит, `> 63` для wide) →
  `BIO_FAULT_SHIFT` (core.c 478) и `BIO_FAULT_WSHIFT` (core.c 631); знаковое расширение
  SAR(S) для отрицательных — core.c 481–484.
- **Сужение wide→int**: выход за `[INT32_MIN, INT32_MAX]` → `BIO_FAULT_NARROW`
  (core.c 655–656). Уширение знаковое (core.c 652).
- **Размер аргумента**: `BIO_FAULT_ARGUMENT_SIZE` (core.c 513).

### 3.4. Границы массивов и строк

- Индекс массива вне диапазона → `BIO_FAULT_BOUNDS` с фиксацией `bad_index`/`bound`
  (core.c 446).
- Индекс строки вне диапазона → `BIO_FAULT_STRING_BOUNDS` (core.c 553).
- Невалидный handle строки → `BIO_FAULT_STRING_HANDLE` (core.c 538/548/564/597).
- Переполнение таблицы строк → `BIO_FAULT_STRING_TABLE` (core.c 570).
- Расход строк сверх бюджета → `BIO_FAULT_STRING_BUDGET` (core.c 575, 602).

### 3.5. Полная модель отказов (fault model)

Единый перечислитель `BioFault` (24 кода 0–23) объявлен в `src/internal.h:118+`, а
человекочитаемые сообщения заданы одним switch в `core.c:256–325`. Код fault, его
назначение и место возбуждения:

| --- | --- | --- | --- |
| 0 | `BIO_FAULT_NONE` | нет ошибки | — |
| 1 | `BIO_FAULT_BUDGET` | исчерпан бюджет инструкций | 257–258; raise 395, 406, 425, 578, 602 |
| 2 | `BIO_FAULT_DIV_ZERO` | деление/остаток на ноль | 260; raise 462 |
| 3 | `BIO_FAULT_DIV_OVERFLOW` | переполнение при делении | 261; raise 464 |

| 7 | `BIO_FAULT_OUTPUT` | WRITE без выходного списка | 271; raise 417 |
| 8 | `BIO_FAULT_READ_SIZE` | READ за границами списка | 272–275; raise 420 |
| 9 | `BIO_FAULT_WRITE_SIZE` | WRITE за границами списка | 276–279; raise 420 |
| 10 | `BIO_FAULT_OUTPUT_SIZE` | output_capacity превышен | 280–283; raise 423 |
| 11 | `BIO_FAULT_ARGUMENT_SIZE` | неверный размер аргумента | 284–287; raise 513 |

| 17 | `BIO_FAULT_PRINT_CAPABILITY` | печать запрещена (нет print) | 307–308; raise 361 |

`execution->failed_node` / `execution->fault`, и выводится с `file:line` посредством
`bio_node_error` (core.c 327–335). Любой fault не валит процесс, а возвращается вызывающему
через `BioError` как читаемое сообщение `BioError.message[1536]` (`include/bio.h:16`),
тем самым аварийная остановка программы не влияет на хост.

### 3.6. Пределы рекурсии/глубины и стека

- `BIO_MAX_DEPTH 256u` (`src/internal.h:21`) — максимальная активная глубина вызовов;
  проверка `execution->depth >= BIO_MAX_DEPTH` → `BIO_FAULT_DEPTH` (core.c 519).
- `BIO_STACK_SIZE 104u` (`src/internal.h:37`) — размер стека в ячейках; исчерпание
  кадра → `BIO_FAULT_FRAME` (core.c 523).
- Для программ с рекурсией под кадры отводится весь пул
  `BIO_MEMORY_CELLS` (`execution.frame_cells = BIO_MEMORY_CELLS`, core.c 695); факт
  рекурсии помечается анализатором (`p->has_recursion = 1`, analyze.c:305), а предельный
  случай «рекурсии нет, но кадр превышает пул» проверяется в analyze.c:352; комментарий
  про `BIO_MAX_DEPTH` / `BIO_MEMORY_CELLS` — `src/analyze.c:287`.

### 3.7. Безопасность памяти ВМ

- Локальные ячейки функции: `BIO_MAX_LOCALS 64u` (internal.h:28) и
  `BIO_MAX_LOCAL_CELLS 65536u` (internal.h:29).
- Полный объём памяти: `BIO_MEMORY_CELLS 262144u` (internal.h:30) — 1 МиБ i32.
- Регистровый файл — «хвост» кадра локальных переменных, адресуется интерпретатором и
  JIT одинаково (core.c 386–388), поэтому каждая новая функция получает свежие регистры.
- Арифметика ведётся на 32/64-бит с явным знаковым прочтением (`signed_value` core.c 338–342,
  `wide_signed` core.c 344–348); индексы сравниваются с реальной ёмкостью до доступа
  (core.c 445–446).

### 3.8. Защита парсера/анализатора от исчерпания ресурсов

- Входной текст ограничен: `BIO_MAX_SOURCE_BYTES` = 4 МиБ (internal.h:27) и длина строки
  `BIO_LINE_SIZE 512u` (internal.h:23), длина пути `BIO_PATH_SIZE 1024u` (internal.h:24),
  длина имени `BIO_NAME_SIZE 64u` (internal.h:25).
- Количество узлов AST: `BIO_MAX_NODES 65536u` (internal.h:19), растёт блоками
  `BIO_NODES_PER_BLOCK 256u` (internal.h:26).
- Таблица символов: `BIO_MAX_SYMBOLS 512u` (internal.h:17); файлов `BIO_MAX_FILES 64u`
  (internal.h:18); генов `BIO_MAX_GENES 256u` (internal.h:16); ремонтов/перестроек
  `BIO_MAX_REPAIRS 1024u` (internal.h:20); глубина импорта `BIO_IMPORT_DEPTH 16u`
  (internal.h:22).
- Литералы: `BIO_MAX_LITERALS 1024u`, `BIO_LITERAL_BYTES` = 256 KiB; строки:
  `BIO_MAX_STRINGS 4096u`, `BIO_STRING_BYTES` = 512 KiB.

### 3.9. Безопасность JIT-кодогенерации (jit_win64.c)

- Короткий относительный переход rel8 применяется только при `disp < 128` (jit_win64.c:39).
- Дальний переход rel32 обрабатывается с проверкой близости; в комментарии явно
  оговорена защита от переполнения смещения (jit_win64.c:76).
- Ветвление учитывает расстояние: `distance > 127` меняет ширину ветки (jit_win64.c:109),
  предотвращая неверный адрес скачка.

### 3.10. Ограничение READ/WRITE белым списком путей (хосты CLI)

В самой ВМ нет понятия «путь»: `READ` копирует только входные байты вызывающего
(`OP_READ` core.c 417–423), `WRITE` — только в выходной буфер. Файловый доступ целиком
находится в хостах командной строки:

- `cli_read_list` читает файл только если `bio_fopen(path, "rb")` успешен; на Windows
  проверяется, что это обычный дисковый файл (`GetFileType == FILE_TYPE_DISK` +
  `GetFileSizeEx`, cli_io.c 70–77), на POSIX — `fstat` + `S_ISREG` (cli_io.c 81–87).
- Файлы больше 1 МиБ (`LIST_FILE_LIMIT 1024u*1024u`, cli_io.c 17) отклоняются
  (cli_io.c 75/98); строка длиннее 511 байт отклоняется (cli_io.c 100); встроенный
  NUL-байт отклоняется (cli_io.c 99). Размер массива ограничен `BIO_LIST_LIMIT`
  (cli_io.c 90).
- UTF-8 вход валидируется `MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, ...)`
  (cli_io.c 108), поэтому невалидные байтовые последовательности не попадают в ВМ.
- `cli_write_list` пишет во временный файл `.codons-<pid>-<serial>.tmp`, вызывает
  `fsync`, затем атомарно публикует через `link(temporary, path)`, который **падает при
  существующем файле назначения** (`EEXIST`, cli_io.c 228–233) — таким образом
  `WRITE` не перезаписывает существующие файлы хоста.

Списки путей для `--input`/`--output` задаёт сам пользователь CLI; программа ВМ не
влияет на имена файлов.

## 5. Остаточные риски и известные пробелы (честно)

1. **C-фаззинг есть, но не в CI.** libFuzzer-харнес парсера/анализатора
   (`tests/fuzz/parser_fuzz.c`, собирается `-DCODONS_FUZZ=ON` под Clang) и
   gcov-ориентированный `tests/fuzz/coverage_fuzzer.py` существуют и прогоняются
   локально; непрерывного санитайзер-джоба в CI пока нет, поэтому регрессии
   устойчивости к искажённым входам отслеживаются вручную.
2. **Сложность анализатора.** Проходы аналитики содержат тонкую логику типов/связывания;
   про её ресурсную верхнюю границу нет отдельного лимита, помимо `BIO_MAX_NODES`.
3. **Бюджет на гранулярности инструкции.** `BIO_EXECUTION_LIMIT` начисляется за
   исполняемые операции, а не за «единичную» стоимость; дешёвые операции (метки, копии
   параметров) могут не декрементировать счётчик, а дорогие строковые операции — нет
   отдельной весовой модели. Итог: реальная CPU-стоимость шага не постоянна.
4. **JIT-самомодификация / переполнение размеров.** Комментарии в jit_win64.c (76, 109)
   сами указывают на деликатность смещений rel8/rel32; целочисленные размеры внутренних
   структур при кодогенерации не везде защищены от переполнения (см. 5.6).
5. **Ограничение путей — на уровне хоста, а не ВМ.** ВМ не знает о путях (есть только
   опкоды `READ`/`WRITE` по переданным буферам); полная защита файлов достигается только
   корректной реализацией `cli_read_list`/`cli_write_list`. Альтернативный хост, который
   передаст ВМ произвольный `BioIO`, получает произвольный доступ в пределах того, что
   намеренно положил в `input`/`output`.
6. **Переполнение внутренних целых размеров.** Арифметика лимитов (`BIO_*`), подсчёты
   размеров пулов и смещений в `core.c`/`jit_win64.c` не везде выполняются с явной
   проверкой переполнения; крайние значения лимитов (например, суммарный размер пула)
   не проходят отдельную проверку в `size_t`.

## 6. Приоритетные рекомендации

### P0 — критично (потенциальная утечка/DoS)

1. **Включить C-фаззинг в CI.** Харнес готов: `cmake -DCODONS_FUZZ=ON` (Clang,
   libFuzzer + ASan/UBSan) собирает `fuzz_parser`; осталось добавить job с прогоном
   по корпусу `tests/fuzz/corpus` и бюджетом `-max_total_time`. Цель — отсутствие
   крашей/утечек на искажённых программах.
   Точка входа: публичное API `bio_compile`/`bio_run` (`include/bio.h`).
2. **Добавить единую проверку переполнения размеров пулов** перед `malloc` в `execute`
   (core.c 697–700, 685–692): утверждать, что `frame_cells * sizeof(*memory)` и
   `string_count` не переполняют `size_t` и укладываются в заявленные лимиты.
3. **Перевести `cli_write_list` на безопасную проверку путей** против TOCTOU: открыть
   целевой каталог (O_NOFOLLOW) и выполнить `linkat`/проверку в каталоге, либо явно
   отказаться от follow симлинков (cli_io.c 201–233).

### P1 — важно (устойчивость, аудит)

4. **Разделить бюджет по весу операций** (строковые операции дороже арифметики), либо
   ввести отдельный байтовый лимит строк уже сейчас (`BIO_FAULT_STRING_BUDGET` core.c 575);
   оценить эффект на гранулярность доставки в `bio_print_helper` (core.c 370–374).
5. **Добавить автономную верификацию JIT-кода** — выгружать сгенерированный блок и
   сравнивать его семантику с интерпретатором на случайных входах (jit_win64.c); либо
   скрыть JIT за флагом по умолчанию до прохождения этого теста.
6. **Зафиксировать верхнюю границу глубины вложенности парсера** на C-стеке явным
   итеративным проходом или явным лимитом глубины, привязанным к `BIO_MAX_DEPTH`.

### P2 — полезно (операционная гигиена)

7. **Задокументировать модель доверия хоста** (что CLI обязан передавать только
   валидированные списки) прямо в `include/bio.h` над `BioIO`, чтобы сторонние хосты
   не ослабляли границы по незнанию.
8. **Добавить негативные тесты на каждый fault** из таблицы раздела 3.5, чтобы
   гарантировать, что каждый код маппится на читаемое сообщение (`tests/test_bio.c`).
9. **Рассмотреть `BIO_MAX_SOURCE_BYTES` как композит** (сумма по всем импортируемым
   файлам), а не только на один файл, чтобы ограничить совокупный ввод.
