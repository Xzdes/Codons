# Архитектура v0.11 и развитие

## Конвейер

```text
.dna + IMPORT
    -> строгий разбор и таблица символов
    -> ASG в блочной арене
    -> связывание CALL.bond с GENE, переходов с LABEL
    -> проверка инициализации по путям, сигнатур и графа вызовов
    -> достижимость от main и предварительная оценка линейных программ
    -> машинный код x64 + релокации CALL/JMP/JZ/JNZ + unwind-таблица
    -> PAGE_EXECUTE_READ + FlushInstructionCache
    -> запуск с локальными данными, списками и общим лимитом шагов / публикация новой версии
```

Компилятор написан на C11 и использует Windows API. Генерируемая программа
состоит из настоящих инструкций процессора, не из байткода интерпретатора.
Интерпретатор существует отдельно для сравнения поведения. `bio_load` заканчивает
работу после проверки графа; `bio_compile` добавляет JIT. Поэтому `check`, `dump`
и `interpret` не выделяют исполняемую память.

## CSV-примеры (0.4)

Команда `test` добавлена на уровне CLI, в `src/cli_test.c`. Язык, C API выполнения,
анализ графа и публикация версий не зависят от формата примеров.
`main` компилируется один раз; число входов задаёт схему CSV: `expected`,
`arg1,expected` либо `arg1,arg2,expected`.

Чтение CSV ограничено 1 MiB, 511 байтами на физическую строку и 1000 примерами.
Проверяются UTF-8, заголовок, количество столбцов, кавычки и диапазон i32.
В памяти сохраняются числа, номера строк и, с 0.9, пути списков. Весь CSV проверяется и закрывается
до первого запуска, поэтому повреждённый CSV не даёт частичного отчёта об успехе.

Числовой пример выполняется через `bio_program_run` с отдельным контекстом лимита.
Файловый пример 0.9 использует существующий `bio_program_run_io`.
Несовпадения и ошибки выполнения не прерывают оставшиеся примеры. Отчёт выводится
по мере выполнения; JSON содержит один объект, его итоговый `ok` и счётчики
записываются после массива результатов. Дополнительные процессы, зависимости
и хранение всех сообщений ошибок в памяти не нужны.

CSV-ошибки имеют отдельные `code`, `file`, `line`, `column` (номер поля).
Сообщения об ошибках исходного `.dna` используют существующую диагностику.
Проверка примеров не подключена автоматически к горячему обновлению
(в 0.11 появился явный шлюз `reload --gate`, см. ниже).

## Файловые CSV-примеры (0.9)

Точный заголовок выбирает режим всего CSV. Прежние 0–2 числовых аргумента и expected
остаются; в новом режиме добавляются input перед expected и expected_output после него.
Пустые пути отклоняются с кодом CSV path. Парсер принимает до пяти ячеек, включая
кавычки для путей с запятыми. Лимиты строк, байтов и числа примеров остаются прежними.

В TestCase сохраняются пути из CSV, каждый ограничен длиной строки 511 байт.
Весь CSV проверяется до исполнения. Перед отдельным примером оба пути разрешаются
от каталога CSV через Unicode API Windows; вход и эталон читаются cli_read_list.
Таким образом, не дублируются правила списка, проверки кодировки, чисел, размера
и типа файла. До успешного чтения обоих файлов программа не запускается.
Ошибки чтения относятся к примеру; обработка следующих строк продолжается.

В BioIO передаётся новый вход и выходная область на BIO_LIST_LIMIT элементов.
Вместимость выхода не зависит от длины эталона: лишние элементы должны дать FAIL
с диагностикой длины, а не ошибку слишком маленького буфера. Старый C API сам
создаёт данные функций, бюджет и внутренний снимок WRITE. После успеха требуется
output_written, чтобы отличать пустой WRITE от отсутствующего. Затем сравниваются
RET, длины и элементы. Первый различающийся элемент общей части имеет приоритет
перед разницей длин; при одинаковой общей части указывается первый отсутствующий
элемент. Номера элементов в отчёте начинаются с единицы.

CaseResult хранит только счётчики и одну пару значений для диагностики. JSON
не включает полные списки; отсутствие элемента обозначается null. Для старого
CSV сохраняются прежние поля отчёта. Новый добавляет input, expected_output и
output с matched, expected_count, actual_count и необязательным difference.
При ошибке файла error дополнен stage=file, field и file; при ошибке исполнения
stage=run. Отсутствие WRITE — ошибка исполнения для файлового теста.

Буферы входа, эталона и результата освобождаются после каждого примера, в том
числе на пути ошибки. Все списки набора одновременно не загружаются. Внешние
списки одного примера занимают до 768 KiB; дополнительно C API временно хранит
снимок выхода до 256 KiB. Метаданные 1000 строк занимают около 1 MiB. Собственная
память языка и её ограничения прежние. Выходные файлы и временные файлы не создаются;
WRITE сравнивается в памяти, входы/эталоны не изменяются. Дополнительных зависимостей,
изменений синтаксиса DNA, машинного кода или C API для этой версии не потребовалось.

## Списки и файловый ввод/вывод (0.7)

Имена в READ/WRITE связываются с существующей таблицей локальных массивов.
READ определяет регистр количества, WRITE читает его. Проверка инициализации
продолжает использовать ту же маску восьми регистров. Обе операции делают оценку
числа шагов динамической, поскольку количество элементов известно при выполнении.

CLI читает и проверяет ограниченный файл перед запуском и передаёт массив i32
через BioIO. Файловые имена не входят в язык и ASG. Один запуск имеет один неизменяемый
входной список и один выходной список; вложенные вызовы используют те же каналы.
Повторный READ копирует вход сначала, последний WRITE заменяет снимок выхода.

Публичные функции с суффиксом _io используют общую обёртку выполнения. Она проверяет
указатели и длины, выделяет отдельный буфер выхода и публикует его в массив вызывающего
только при успехе всего вызова. Это сохраняет прежние данные после ошибки, даже если
WRITE уже был исполнен. Старые функции вызывают эту обёртку без каналов. Runtime
удерживает выбранный снимок программы на время вызова, как и раньше.

В JIT READ/WRITE используют только временные регистры R10, R11, ECX и EAX.
Сначала проверяются наличие канала и вместимость. После обычного шага операции
проверяется и списывается бюджет копирования целиком: один шаг на элемент. Затем
выполняется ограниченный цикл MOV; C-функции из машинного кода не вызываются.
Интерпретатор использует те же условия и списание, затем memcpy. Пустой перенос
разрешён. Если оставшегося бюджета недостаточно, копирование не начинается.

Списки ограничены 65536 числами; они выделяются отдельно от 1 MiB локальных данных.
На уровне C API один входной и один выходной массив могут принадлежать вызывающему;
частный буфер результата занимает до 256 KiB. CLI дополнительно хранит вход, выход
и текст для сохранения. Все временные буферы освобождаются после вызова.

src/cli_io.c проверяет вход: обычный дисковый файл, до 1 MiB, до 511 байт на строку,
UTF-8, по одному i32 на непустой строке. Проверка перед выполнением исключает запуск
на частично прочитанном повреждённом списке. Она не задаёт таймаут дисковой операции.
После успеха создаётся соседний временный файл через CREATE_NEW; после полной записи
и FlushFileBuffers он публикуется MoveFileExW без MOVEFILE_REPLACE_EXISTING.
Это сохраняет существующий результат и при конкурирующей публикации.
Обработанные ошибки удаляют временный файл; принудительное завершение процесса
может оставить временный файл. Альтернативные потоки NTFS для выходов не разрешены.
Файловые флаги доступны только run/interpret; test/live сохраняют прежний CLI.

## ASG и арена

`CodonNode` сохраняет поля из исходной идеи: опкод, два числовых операнда,
`next` и `bond`. Добавлены координаты исходника, индекс узла, смещения машинного кода
и релокации, признаки достижимости и восьмибитная маска инициализации регистров.
В 0.8 поле `call_array` хранит необязательный массив CALL: ноль либо индекс + 1.
При разборе это индекс символа, после связывания — индекс локального объявления.
`GENE` является узлом графа, `END` — синтаксическим ограничителем.
Цепочка `next` задаёт порядок исходника, `bond` связывает `CALL` с целевой функцией,
а `JMP`/`JZ`/`JNZ` — с локальной меткой. Обратные рёбра допускают циклы внутри функции.

Арена выделяет блоки по 256 узлов. Адреса узлов стабильны: нет `realloc`, который
мог бы инвалидировать `next` или `bond`. Переполнение бюджета обрывает компиляцию.
Все блоки принадлежат конкретной версии программы и освобождаются вместе с ней.

Это устраняет отдельное выделение на каждый узел, но не гарантирует попадания
в кэш и не заменяет дисциплину владения памятью. ASG также не является
автоматически лучшей заменой AST: граф выбран ради явных связей и эксперимента.

## Локальные данные (0.6)

`VAR` и `ARRAY` разрешены только в начале тела функции. Небольшая таблица `BioLocal`
в `BioGene` хранит имя, смещение в ячейках i32, размер, начальное значение и вид данных.
Линкер заменяет имена в операциях индексами этой таблицы и проверяет соответствие
операции переменной или массиву. Объявления остаются в ASG для дампа и диагностики.
Они проходят анализ потока без чтения и записи регистров.

Каждая переменная и ячейка массива инициализирована при входе, поэтому для них
не требуется отдельный анализ присваиваний. `GET`/`AGET`/`LEN` определяют регистр;
`SET` читает значение, `AGET` — индекс, `ASET` — индекс и значение. Это учитывается
в существующей восьмибитной проверке регистров, включая совпадающие операнды.

Размер локальных данных известен до запуска. После проверки графа вызовов:
`memory(g) = local_cells(g) + max(memory(reachable callees))` (максимум пустого набора — 0).
Проверяется максимум для `main`: до 262144 ячеек i32 (1 MiB), до 65536 ячеек
и 64 объявлений на функцию. Последовательные вызовы занимают один и тот же участок;
недостижимые вызовы не увеличивают область данных `main`.

Обёртка C API выделяет один блок на запуск и освобождает его при успехе или ошибке.
Если данных нет ни у main, ни у достижимых вызываемых функций, выделение не нужно.
Родитель передаёт дочерней функции указатель сразу за своими ячейками. Каждый вызов
сначала обнуляет свой участок, затем записывает ненулевые начальные значения VAR.
На инициализацию списывается один шаг за ячейку; исчерпание бюджета сообщает строку GENE.
Память для графа, машинного кода и данных принадлежит разным объектам; данные не
попадают в исполняемые страницы и не разделяются между параллельными запусками.

Проверка индекса использует беззнаковое сравнение с длиной: отрицательное i32 также
отклоняется. Только после успешной проверки выполняется доступ к элементу. Ошибка
сохраняет индекс и длину в контексте запуска и возвращается обычным путём.
Глобальных данных, изменения размера и пользовательских указателей нет.

## Передача массивов (0.8)

`PARAM name r0` добавляет в таблицу BioLocal массив с `is_parameter = 1` и нулём
собственных ячеек. Объявление разрешено среди начальных VAR/ARRAY, только одно,
в функции i32/1 или i32/2, кроме main. `BioGene.has_array` входит в сигнатуру.
CALL принимает `array,rN` или `array,rN,rM`; числовые аргументы по-прежнему попадают
в r0/r1. Проверка инициализации читает только регистры, линкер проверяет наличие
массива в сигнатуре и связывает имя с ARRAY или PARAM вызывающей функции.

При выполнении CALL проверяет без знака, что первое число не больше доступной
длины массива. Это отклоняет и отрицательные i32. Затем передаёт указатель на
первый элемент и проверенную длину. Ошибка длины указывает CALL, ошибка доступа —
AGET/ASET. Нулевую длину передавать можно; диагностика индекса отдельно описывает
пустой массив, не вычисляя несуществующий последний индекс.

Пара указатель/длина сохраняется на весь вызов. LEN читает сохранённую длину,
AGET/ASET и READ/WRITE используют её как границу. Изменения r0 и вложенные вызовы
не меняют эту пару. Переданный PARAM можно сузить при следующем CALL; родитель
сохраняет свою границу. Собственные ARRAY функции остаются отдельными объектами.
Начальная инициализация касается только собственных ячеек, поэтому не стирает
входной массив. Память и шаги на копирование/обнуление PARAM не расходуются.
Формулы памяти и бюджета вызовов остаются прежними; объявление PARAM стоит 0 шагов.

В интерпретаторе пара передаётся отдельными аргументами interpret_gene. В JIT это
внутренний контракт прямого CALL: R10 — указатель, R11D — проверенная длина.
Пролог сохраняет их до инициализации собственных данных. Публичный C API прежний:
main не принимает PARAM, скрытые регистры массива ему не нужны.
Все ссылки ведут в собственный массив активного предка; их нельзя вернуть,
сохранить между вызовами или использовать после возврата владельца.
Блок данных и контекст бюджета остаются отдельными для каждого запуска.

## Проверка ветвлений

Метки разрешаются в пределах функции, вперёд и назад. Дубликаты и неизвестные
цели отклоняются. У `JMP` один преемник — цель, у условного перехода два — цель
и следующая инструкция, у `RET` нет преемников. Выход достижимого пути в `END`
считается ошибкой. Неиспользуемые ветки не требуют фиктивного `RET`.

Анализ использует очередь существующих узлов и маску из восьми бит. На входе
известны только аргументы функции. Присваивание добавляет бит, а соединение путей
берёт пересечение масок. Обход продолжается до устойчивого состояния, затем
каждое достижимое чтение проверяется по полученной маске. После обнаружения узла
его маска может только терять биты; это ограничивает повторную обработку и при циклах.
Обе стороны условного перехода считаются возможными; свёртки констант нет.
Отдельные базовые блоки, SSA и новый промежуточный язык для этого не потребовались.

## Плазмиды и апоптоз

`IMPORT` разрешается относительно файла, где он встречается. Полные нормализованные
пути сравниваются без учёта регистра; повторное подключение завершённого модуля
пропускается, подключение уже разбираемого модуля считается циклом. Все имена функций
пока находятся в общем пространстве имён. Дубликаты отклоняются.

Пути не идентифицируются по Windows file ID: алиасы через hardlink/junction могут
попасть в обработку как разные файлы. Даже в таком случае лимиты глубины, файлов,
байтов и узлов ограничивают обработку.

После связывания проверяется весь граф вызовов. До 0.14 рекурсивные циклы
запрещались; теперь они разрешены и ограничены во время выполнения (см. ниже),
а статический обход просто помечает программу как рекурсивную и прекращает
накапливать по циклическому ребру суммы шагов и памяти.
Макросов и генераторов пока нет, поэтому защита от их бесконечного раскрытия
остаётся задачей следующего этапа.

Для линейных функций обход графа считает суммарное количество инструкций с учётом каждого
вложенного вызова: `steps(gene) = local_cells + own_instructions + sum(steps(each CALL target))`.
Значение насыщается на `1 000 001`, поэтому экспоненциальный граф не переполняет
счётчик. Лимит в миллион применяется к достижимому от `main` выполнению.
Недостижимые дорогие функции не мешают запуску короткого `main`.
При достижимом переходе, READ/WRITE или вызове функции с динамической оценкой она помечается
неизвестной: `BioStats.dynamic_steps = 1`, `execution_steps = 0`; CLI отдаёт `null`.

Каждый запуск создаёт на стеке отдельный `BioExecution`: остаток бюджета
`uint64_t remaining = 1000000`, индекс ошибки `uint32_t failed_node = UINT32_MAX`
и вид ошибки `uint32_t fault = BIO_FAULT_NONE`. В 0.6 добавлены `int32_t bad_index`
и `uint32_t bound` для диагностики массива. В 0.7 добавлены указатели списков,
длины, вместимость выхода и признак выполненного WRITE; внутренний контекст занимает 64 байта.
Все вложенные вызовы получают один контекст. Перед каждым исполняемым кодоном
проверяется остаток, затем списывается шаг. `LABEL`, `GENE`, `END`, `IMPORT`, `VAR`,
`ARRAY`, `PARAM` как узлы шагов не расходуют; инициализация данных при входе учитывается отдельно.
Бесконечный цикл обязательно содержит расходующий шаг переход.
Счётчик есть и в JIT, и в интерпретаторе, в том числе у линейных программ.

При нулевом остатке следующий кодон записывает свой индекс и вид ошибки, затем возвращается.
Вызывающие функции сразу распространяют ошибку до C API; частичное значение
не записывается в выходной аргумент. Индекс находится в арене для диагностики
`файл:строка`. Счётчики не хранятся в общей программе, поэтому параллельные вызовы
не влияют на лимиты друг друга. Нет таймера, исключений или контролирующего потока.
Деление на ноль, переполнение частного, неверный счётчик сдвига, выход за границы и ошибки списков используют
тот же путь возврата ошибки. Публичный C API сохраняет выходное число неизменным.

Все внешние пути в C API — UTF-8; внутри файловых операций они преобразуются
в UTF-16. Нормализация использует `GetFullPathNameW`, открытие — `_wfopen`,
сравнение — `CompareStringOrdinal` без учёта регистра. Триплетный синтаксис импорта
по-прежнему не включает строковые литералы с пробелами.

## Pseudogenes GC

От `main` по достижимым `CALL` помечаются используемые функции.
Генератор выдаёт код только для них и только для достижимых узлов внутри них.
Это исключение неиспользуемых функций из машинного кода, а не полноценный GC.
Узлы недостижимых функций остаются в арене до освобождения версии: их данные
полезны для диагностики и проверки совместимости при обновлении.
Уменьшение памяти самого ASG потребует отдельной компактизации арены и переноса рёбер.

## Windows x64

Аргументы 1–4 поступают через ECX, EDX, R8D и R9D, результат возвращается в EAX.
Аргументы 5 и 6 — указатель на общий `BioExecution` запуска и база локальных
данных текущего вызова — передаются на стеке (стековые аргументы Win64);
пролог читает их с `[rsp+160]` и `[rsp+168]`. Контекст и база локалов кэшируются
в callee-saved регистрах RBX и RSI на всё тело функции (0.11): вложенные вызовы
сохраняют их автоматически, перечитывание со стека на каждой инструкции исчезло.
В каждой функции резервируются 104 байта стека: 32 байта обязательной области
параметров, 16 байт исходящих стековых аргументов (32/40), 32 байта виртуальных
регистров r0..r7 (смещения 48–79) и, начиная с 0.8, 8 байт указателя PARAM
и 4 байта его длины (80/88); оставшиеся 12 байт — запас и выравнивание.
Перед вложенным вызовом RSP выровнен на 16 байт.
Точка входа `main` использует тот же контракт для 0–4 входных значений.
`EQ` и `LT` используют сравнение с материализацией результата 0/1,
`MIN` и `MAX` — условное перемещение. Все сравнения знаковые.
`JZ`/`JNZ` сравнивают локальный регистр с нулём и выполняют условный переход rel32.

В 0.5 `DIV`/`MOD` расширяют оба i32 до знаковых i64 (`CDQE`, `MOVSXD`) и выполняют
`CQO; IDIV RCX`. Делитель проверяется до `IDIV`; даже крайняя пара i32 даёт частное,
помещающееся в i64. Для `DIV` отдельно проверяется представимость частного в i32;
`MOD` берёт остаток из EDX. Поэтому деление не требует обработчика аппаратных исключений.
Интерпретатор также использует i64 для деления и остатка.

Побитовые операции работают с 32 битами, логические нормализуют оба значения
до 0/1 через `SETNE`. Сдвиги проверяют счётчик без знака на `<= 31` перед
`SHL`/`SHR`/`SAR`: отрицательные значения тоже отклоняются. В интерпретаторе
сдвиг вправо со знаком реализован через uint32 и явное заполнение старших битов,
без зависимости от правил знакового сдвига конкретного компилятора C.

Виртуальные регистры лежат в стеке, поэтому не теряются при вызове других функций.
В 0.11 добавлены кэширование контекста в RBX/RSI и peephole-исключение повторных
загрузок (~×2,4 на циклах); полное распределение r0..r7 по физическим регистрам
остаётся возможным следующим шагом после появления оптимизирующего IR.

`CALL` и локальные переходы используют относительное смещение rel32, заполняемое после
раскладки всех достижимых функций. Весь буфер занимает менее 17 MiB,
поэтому такие смещения помещаются в 32 бита. Для функций регистрируется
`RUNTIME_FUNCTION` через `RtlAddFunctionTable`; общий `UNWIND_INFO` описывает
пролог `push rbx; push rsi; sub rsp, 104` тремя unwind-кодами. Перед освобождением
кода таблица удаляется. Ошибки возвращаются через обычный эпилог
`add rsp, 104; pop rsi; pop rbx; ret`. Перед CALL база локалов кали вычисляется
из RSI прибавлением размера собственных данных и пишется в исходящий слот стека.
Peephole-кэш помечает, какой виртуальный регистр сейчас в EAX, и пропускает
повторные загрузки; на метках-точках слияния кэш сбрасывается.

Сырые байты `emit` начиная с 0.3 требуют скрытого контекста и не включают обёртку,
которая создаёт его и проверяет ошибку. Они не являются самостоятельной функцией
или стабильным интерфейсом. Для встраивания предназначены
`bio_program_run` и `bio_runtime_run`; в байтах нет указателей на узлы арены.
В 0.6 контекст расширен индексом и длиной, добавлен аргумент с памятью для данных.
В 0.7 контекст содержит также каналы списков; READ/WRITE не содержат абсолютных адресов.
Это не публичный ABI; C API сам выделяет и освобождает область нужного размера.

Буфер сначала имеет права READWRITE, после заполнения — EXECUTE_READ.
Одновременных прав записи и исполнения нет. После смены защиты вызывается
`FlushInstructionCache`, а все ошибки Windows API приводят к отказу компиляции.

## DNA-Repair 0.10

Репарация включается только флагом `--repair`. Парсер сначала восстанавливает
однозначное неиспользуемое `_`. Если триплет или его связь с графом неоднозначны,
узел заменяется на `OP_QUARANTINE`; синтезировать значение, тип, функцию или
переход запрещено. Семантическая проверка тем же способом карантинирует неизвестные
цели, несовместимые локальные данные, чтение неинициализированного регистра и
достижимое падение с конца функции. После каждой замены анализ потока запускается
заново, поэтому JIT видит только согласованный граф.

Карантин терминальный: у него нет исходящих рёбер и нет записи в виртуальные
регистры. Он выполняется одинаково в интерпретаторе и JIT, записывая
`BIO_FAULT_QUARANTINE` и индекс исходного узла. `execution_ok` возвращает
диагностику файла и строки; публичный журнал ремонта отдельно хранит причину.
Лимит журнала — 1024 записи, после чего сборка прекращается как ограничение
ресурсов. Исходные файлы не модифицируются.

Границы репарации намеренно узкие: повреждение объявления функции, импорта,
кодировки, циклов импортов и бюджетов не превращается в исполняемую программу.
Так аварийное восстановление не становится способом незаметно изменить модель
владения, таблицу символов или границы памяти.

## DNA-Repair и владение версиями

1. Полный новый `.dna` и его модули собираются в отдельную версию. Ошибка не меняет runtime.
2. Под блокировкой сравниваются сигнатуры с текущей опубликованной версией:
   имя, число числовых аргументов и наличие PARAM. Имя самого параметра не влияет.
3. Указатель `active` заменяется согласованно с захватом ссылок читателями.
4. Ссылка runtime на старую версию снимается. Действующие вызовы сохраняют свои ссылки.
5. Последний пользователь версии освобождает код, unwind-таблицу и арены.

Захват указателя и увеличение счётчика ссылок выполняются под одной блокировкой.
Один атомарный exchange без этого протокола был бы недостаточен: другой поток
мог бы освободить версию между чтением указателя и увеличением счётчика.
Прямые внутренние `CALL` всегда остаются в пределах выбранного снимка программы.

`bio_runtime_create` сохраняет собственную ссылку на входную программу. Вызывающий
код обязан освободить свою ссылку через `bio_program_release`. Для прямых
`bio_program_run`/`bio_program_interpret` вызывающий должен удерживать программу живой.
`bio_runtime_destroy` вызывается только после завершения всех обращений к runtime.
`BioError` принадлежит вызывающему; одновременные операции используют разные экземпляры.
В API выполнения 0.2 отделены статус операции и результат i32. Несовпадение числа
аргументов отклоняется до вызова машинного кода, выходное значение остаётся прежним.
Runtime принимает только программу с подготовленным JIT.

Поддержка смены функции внутри долгоживущего вызова потребует другого контракта:
стабильных точек входа, таблицы диспетчеризации, описания состояния и точек обновления.
В этой версии вызов, начатый до обновления, остаётся в старой программе до возврата
или ошибки выполнения. Любая ошибка освобождает ссылку на версию обычным путём.

## Проверки доверия 0.11

`verify` компонирует существующие публичные вызовы: один разбор, один JIT, затем
`bio_program_run_io` и `bio_program_interpret_io` с отдельными контекстами и
выходными буферами. Согласие означает равенство статуса, результата, снимка
`WRITE` и — при ошибке — текста диагностики с файлом и строкой. Новых путей в
компиляторе нет; команда только сравнивает два существующих бэкенда.

Шлюз `--gate` в `live reload` разделяет обновление на компиляцию, проверку и
публикацию. Проверка переиспользует `cli_test` без изменений; публикация вынесена
в `bio_runtime_publish`, который повторяет контракт сигнатур `bio_runtime_reload`
и удерживает собственную ссылку на кандидата. Сам `bio_runtime_reload` выражен
через `bio_compile` + `bio_runtime_publish`. Кандидат, не прошедший CSV,
отклоняется до блокировки публикации; активная версия не затрагивается.

Охраны JIT переведены с rel8 на ближние переходы rel32 (формы `0F 8x`), поэтому
размер функции больше не ограничен дистанцией 127 байт до аварийного выхода.
Оценка буфера генерации поднята до 288 байт на узел; переполнение по-прежнему
фиксируется как внутренняя ошибка, а не порча кода.

## Строки 0.12

Строка — неизменяемая последовательность байтов `{const uint8_t *data; uint32_t length}`.
Регистр хранит хэндл: индекс i32 в таблице строк запуска, а не указатель. Литералы
программы хранятся один раз в `BioProgram` (`literals` + бамповый `literal_pool`);
`SLOAD` несёт индекс литерала в `arg2`. Разбор полей и удаление комментариев учитывают
кавычки: пробелы и `#` внутри литерала не делят триплет.

Перед входом в программу со строками (`uses_strings`) `execute` выделяет таблицу
на 4096 записей (64 KiB) и пул результатов на 512 KiB; начало таблицы заполняется
литералами. Новые поля `BioExecution`: `strings`@64, `string_count`@72,
`string_pool`@80, `pool_used`@88, `pool_capacity`@92; смещения фиксированы
`_Static_assert`, как и у полей списков. JIT не выделяет память: `SCAT` пишет
результат по бамповому курсору пула и добавляет запись в таблицу.

Проверки до обращения к памяти, в обоих бэкендах побайтово одинаковые: хэндл —
беззнаковым сравнением с `string_count` (ловит и отрицательные), индекс `SGET` —
с длиной, `SCAT` — сначала таблица (4096), затем пул (помещается ли результат),
затем бюджет шагов. `SCAT` стоит 1 + число копируемых байтов шагов,
`SEQ` — 1 + min(длины) + 1; тарифы совпадают с `READ`/`WRITE`. Пул 512 KiB меньше
бюджета в миллион шагов, поэтому исчерпание пула достижимо и тестируется.

JIT использует только волатильные регистры Win64 (RAX, RCX, RDX, R8–R11) плюс
сохранённые прологом RBX/RSI. **Урок 0.12:** первая версия `SCAT` использовала
RDI как курсор таблицы; RDI в Win64 — callee-saved, поэтому при -O3 вызывающий
код держал в нём живое значение и куча портится. При -O0 и в CLI-тестах ошибка
не проявлялась: нашли её связкой «ядовитые буферы 0xAB + полное сканирование после
запуска» и аппаратной точкой наблюдения (Dr0), которая доказала, что JIT-код
в буфер не пишет, а пишет CRT. Теперь адрес записи таблицы считается через RAX.
Любой новый опкод JIT обязан обходиться волатильными регистрами либо расширять
пролог и `UNWIND_INFO`.

Литеральные байты читаются через указатели в `BioString` (в `literal_pool`),
результаты — из пула запуска; самосцепление и цепочки `SCAT` безопасны, потому что
источники неизменяемы, а область результата не пересекается с читаемой.

## Хост-возможности и PRINT 0.13

`PRINT rN _` — первый кодон, выходящий за пределы процесса. Внешний мир описывается
моделью capabilities: хост явно заполняет поля `BioIO` (вход, выход, печать),
а программа без выданного канала получает ошибку выполнения. Печать — это обратный
вызов `int (*print)(void *user, const unsigned char *bytes, size_t length)` плюс
`print_user`; новые поля `BioExecution`: `print`@96 и `print_user`@104, смещения
зафиксированы `_Static_assert`. `NULL` означает «канала нет»:
`PRINT requires a host print capability`.

Семантика целиком живёт в одном C-хелпере `bio_print_helper`, который вызывают оба
бэкенда: это единственный источник истины, и паритет сбоев гарантирован по
построению. Порядок проверок: capability → хэндл → бюджет (вся длина проверяется
до отправки, частичной записи не бывает) → списание → обратный вызов. Тариф —
1 шаг за кодон плюс по шагу за байт; узловой шаг списывается централизованно
(`guard_step` / цикл интерпретатора), байты — хелпером. Нулевая длина не вызывает
обратный вызов. Отказ колбэка — `the host print callback failed`.

`emit_print` — первый вызов C-кода из сгенерированного JIT-кода. Кадр генов
спроектирован так, что тело держит RSP кратным 16 и резервирует теневое
пространство 0..31, поэтому обычный `call` по абсолютному адресу (imm64)
корректен по Win64 ABI: `mov rcx,rbx; mov edx,[slot]; mov r8d,node;
mov rax,imm64; call rax`. Хелпер при сбое сам пишет `failed_node` и код ошибки
и возвращает 0; JIT тогда кладёт 0 в EAX и уходит в общий эпилог. Аргументы —
только волатильные регистры (урок RDI из 0.12), а после вызова эмиттер сбрасывает
кэш регистров: C-код вправе испортить всё волатильное.

CLI всегда выдаёт канал: текстовые `run`/`interpret` печатают в stdout во время
работы, `--json` накапливает байты в растущем буфере и отдаёт полем `printed`
(экранируются `"`, `\` и байты < 32; остальное идёт как есть — ожидается UTF-8).
`verify` накапливает печать обоих бэкендов и считает расхождение байтов
расхождением результата; в текстовом режиме согласованный вывод печатается один
раз. Тестовый прогон по CSV выдаёт канал-«пылесос`: примеры сравнивают данные,
печать отбрасывается. Бюджет ограничивает суммарный вывод миллионом байтов
(шаг на байт), поэтому буфер захвата растёт не выше этой границы.

## Рекурсия 0.14

До 0.14 память локалей была стекообразной, но статически измеренной: память
под локали выделялась ровно по самой глубокой цепочке вызовов (это возможно,
только пока граф ацикличен), а циклы в графе вызовов отклонялись при компиляции.
В 0.14 циклы разрешены, а пределы перенесены во время выполнения.

Новые поля `BioExecution`: `frame_used`@112, `depth`@116, `frame_cells`@120
(смещения зафиксированы `_Static_assert`). Инвариант: при входе в ген
`frame_used` равен сумме локальных ячеек всех активных кадров, а база локалей
гена — `пул + frame_used - local_cells`; оба бэкенда поддерживают этот инвариант
на каждом `CALL`. `depth` считает активные гены; `main` занимает первый кадр.

Проверки на `CALL` (порядок совпадает в обоих бэкендах): размер массива-
аргумента → глубина (`depth >= 256` → `call depth limit reached`) → память
(`need > frame_cells - frame_used` → `call frame memory exhausted` с деталями
need/left) → фиксация (`frame_used += need; ++depth`) → вызов → безусловный
откат на обоих исходах (`frame_used -= need; --depth`) → распространение сбоя.
В JIT проверки эмитируются инлайн теми же примитивами, что и остальные гарды;
количество ячеек вызываемого гена известно на этапе эмиссии.

Пул кадров: для ацикличных программ выделяется точное статическое значение
(`memory_cells` от `main`, как раньше); для программ с циклом — фиксированные
262144 ячейки (1 MiB). Компилятор помечает циклическое ребро в DFS
(`visit == 1` на цели): `has_recursion = 1`, `dynamic_steps = 1` вместо
статических сумм; статика по ацикличным рёбрам не меняется. Статические пределы
глубины отменены: цепочка из 256 разных генов компилируется и работает, а
256-й вложенный вызов отклоняется уже в рантайме. Предел 256 кадров — это
≤ 32 KiB нативного стека JIT и сравнимый объём у интерпретатора, что безопасно
даже на небольших стеках потоков.

Мёртвые гены могут содержать рекурсию: они не компилируются и не выполняются.

## Широкие регистры 0.15

i64 живёт в отдельном классе регистров `w0..w3`, как строки — в своём: никакой
неявной типизации, `r0..r7` остаются i32. Пересечение классов только через два
явных кодона: `WIDEN wN rM` (знаковое расширение) и `NARROW rN wM` (ошибка
выполнения, если значение не помещается в i32). Сравнения `WEQ`/`WLT` пишут флаг
0/1 в обычный регистр — ветвления остаются i32-шными.

Литералы i64 не помещаются в 32-битные поля кодона, поэтому `WLOAD` хранит индекс
в таблице `wide_literals` программы — как `SLOAD` для строк. Дамп печатает литерал
десятичным текстом, `strtoll` точно покрывает весь диапазон, включая `INT64_MIN`.

Анализатор инициализации расширил битовую маску узла до 12 бит: 0-7 — `r0..r7`,
8-11 — `w0..w3`; meet-операция не изменилась. (В 0.16 маска выросла до
динамических битсетов — см. следующий раздел.)
Интерпретатор держит `uint64_t w[4]`; знаковые операции (`WDIV`, `WMOD`, `WLT`,
`WMIN`, `WMAX`, `WSAR`) читают биты через `memcpy`-хелпер `wide_signed`, чтобы не
зависеть от implementation-defined поведения. Сдвиг `WSAR` реализован битово,
без знаковых сдвигов C.

В JIT кадр вырос с 104 до 136 байт: `w0..w3` — слоты по 8 байт в `rsp+96+8w`,
все доступы с префиксом REX.W. `sub/add rsp,136` перешли на imm32-форму (136 не
помещается в знаковый imm8), а смещения стековых аргументов 5/6 выросли до
`[rsp+192]`/`[rsp+200]`. Кадр 136 байт превышает 128-байтный потолок
`UWOP_ALLOC_SMALL`, поэтому UNWIND_INFO использует `UWOP_ALLOC_LARGE` со слотом-
полезной нагрузкой 17 (= 136/8). Заодно исправлена латентная ошибка: код регистра
`rbx` в записи `UWOP_PUSH_NONVOL` был 0 (rax) вместо 3. Корректность метаданных
по-прежнему проверяется настоящим `RtlVirtualUnwind` в тестах.

64-битное `idiv` падает аппаратно на паре `INT64_MIN / -1` (в отличие от i32,
где JIT расширял операнды до 64 бит), поэтому `WDIV`/`WMOD` эмитируют явную
проверку этой пары после проверки нуля. `NARROW` в JIT — трюк
`movsxd rdx,eax; cmp rdx,rax`: знаковое расширение младших 32 бит обязано
совпасть с исходным значением.

## Регистры в кадре и структуры 0.16

Виртуальные регистры `rN` переехали из фиксированного JIT-кадра в пул локалей:
`rN` — это ячейка `[rsi + 4*(reg_base + N)]`, где `reg_base` — число объявленных
ячеек (`VAR`/`ARRAY`), замороженное при `END` функции. Раз рекурсия 0.14 уже
выделяет кадры из пула, каждый уровень автоматически получает свежий регистровый
файл; интерпретатор просто берёт `r = memory + reg_base`. Потолок — 256 регистров
(`r0..r255`): все упаковки операндов 8-битные, предел честно документирован.

Стоимость по шагам не выросла: обнуляются и заряжаются в бюджет только
объявленные ячейки (`reg_base` штук), а регистры — нет: статическое доказательство
«запись до чтения» делает обнуление наблюдаемо бесполезным, и старый JIT его
никогда не делал. `local_cells = reg_base + reg_count` входит в
`memory_cells`/пул кадров 0.14, так что предельные тесты пересчитаны, а не
ослаблены.

Анализатор инициализации перешёл с фиксированной маски на динамические битсеты:
поле `CodonNode.flow` — смещение слова в арене `uint64_t` на всю функцию
(узлы × слова; биты `0..reg_count-1` — регистры, следующие четыре — `w0..w3`).
Арена стартует верхним элементом «всё инициализировано» (`0xFF…`), входной узел
получает только биты арности, meet — побитовое И по словам. Сообщения об ошибках
теперь называют точный регистр: `read of uninitialized register r200`.

`CALL` до связывания хранит арность в `n->flow` и пакует до четырёх регистров
в 8-битные поля `arg2`; после связывания (где `arg1` — уже индекс гена) арность
читается из сигнатуры вызываемого. Все потребители — анализатор, дамп, оба
бэкенда — используют эту форму, поэтому аргументы из `r12` или `r200` проходят
без потерь.

JIT-кадр вернулся к 104 байтам: тень 0-31, исходящие аргументы 32/40, вид PARAM
48/56, широкие регистры `w0..w3` — слоты `rsp+64+8w`. Пролог снова в imm8-форме,
UNWIND_INFO снова `UWOP_ALLOC_SMALL` (с исправленным кодом регистра `rbx` = 3 из
0.15), а проверка `RtlVirtualUnwind` продолжает сторожить согласованность кадра
и метаданных.

`STRUCT p x,y` — чистый сахар парсера: каждое поле становится отдельным узлом
`VAR` с точечным символом (`p.x`, `p.y`), одна ячейка, ноль. Резолвер, дамп
(`VAR p.x 0`), бэкенды и лимиты ничего о структурах не знают. Имя `p` само
локалью не становится; повторное объявление поля ловит обычная проверка
дубликатов.

## Литеральные операнды и машинный интерфейс ошибок 0.17

У бинарных i32-опкодов второй операнд может быть литералом: узел хранит его в
`arg2` с флагом `arg2_literal` (поместился в выравнивание после трёх `uint8_t`).
Литерал не является регистром ни для одного потребителя: `reads()` его
пропускает, `node_registers` не учитывает, интерпретатор и JIT берут значение
напрямую. JIT-формы: `81 /digit id` для арифметики, `imul`/`cmp` с imm32,
`C1 /digit ib` для сдвигов, `mov edx,imm32` + `cmov` для `MIN`/`MAX`.
Литеральный ноль-делитель и сдвиг вне 0..31 отклоняются ещё в парсере —
статически известный сбой не доезжает до выполнения.

Сообщения об ошибках стали инструкциями: типовые тексты несут готовое
исправление, а JSON-ошибки — поле `line_text` с исходной строкой (пропускается,
если строка не валидный UTF-8). Добавлены `test --init` (CSV-заголовок из
арности и каналов через `bio_program_channels`) и `fix` (репарация на диск
без перезаписи). Машинный справочник `LLM.md` и харнес `tests/llm_eval/`
замыкают цикл: модель пишет по справочнику, компилятор отвечает подсказками,
харнес измеряет классы сбоев.

## Следующие этапы

Управление потоком реализовано в 0.3 на существующем графе. Следующие изменения
стоит выбирать по небольшим практическим задачам и ошибкам пользователей.
Оптимизатор, дополнительные типы, частичная репарация функций и самостоятельные
PE-файлы остаются возможными направлениями, но не требуются для работы текущей версии.

Триплетный синтаксис может уменьшить долю синтаксических ошибок, но корректность
алгоритма и типов всё равно проверяется отдельно. Утверждения «0% сбоев»,
«полное отсутствие утечек» и «нулевой даунтайм» требуют измеримых определений
и проверки; они не следуют из биологической метафоры.
